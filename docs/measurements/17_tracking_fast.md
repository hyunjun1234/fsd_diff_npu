# 빠른 물체 추적과 카메라 끊김 처리

이 문서는 마주 오는 차(상대 25 m/s)에서 ID가 바뀌던 원인을 숫자로 찾고 robust 추적기를 칼만 필터 판으로 고친 결과, 측면 카메라의 차 중심 추정 옵션, 카메라 끊김 복구를 정리한 기록입니다. 측정일은 2026-11-25입니다. 추적 지표는 맥 시뮬레이션(15fps, 225프레임, seed 0~4 합계)이고, 끊김 복구와 추적기 계산 시간은 파이 5에서 쟀습니다. 카메라 보정 전이라 거리 정확도로는 판정하지 않았고, DX-M1은 쓰지 않았습니다.

## 1. 요약

robust 추적기를 칼만 필터(위치, 속도 상태와 공분산), 마할라노비스 거리 문턱, 헝가리안 짝짓기, 속도를 본 겹침 정리, 사각지대 예측 유지로 고쳤습니다. 기본 장면과 마주 오는 차 장면, 카메라 2대와 4대 모두에서 ID 바뀜, 물체당 트랙 수, 놓친 프레임 비율, 중복 표시가 예전 robust보다 줄었고 나빠진 지표는 없습니다. 기본값(basic)은 바꾸지 않았습니다.

| 조건 | ID 바뀜 basic / 예전 robust / 새 robust | 마주 오는 차 몫 |
|---|---|---|
| 카메라 2대, 기본 장면 | 381 / 48 / 20 | 해당 없음 |
| 카메라 4대, 기본 장면 | 487 / 51 / 11 | 해당 없음 |
| 카메라 2대, 마주 오는 차 | 608 / 123 / 76 | 187 / 76 / 33 |
| 카메라 4대, 마주 오는 차 | 697 / 123 / 55 | 196 / 61 / 27 |

14 문서와 같은 조건(카메라 4대, 마주 오는 차, seed 0~2)에서는 ID 바뀜이 79회에서 33회, 그중 마주 오는 차가 37회에서 17회가 되었습니다.

카메라 끊김은 `run_demo.py --cam-retry 초`로 넣었습니다. 파이에서 가짜 측면 카메라 하나를 파일 끝에서 끊기게 하고 20초 돌렸을 때 두 번 끊기고 두 번 다시 열렸으며, 그동안 그 칸은 NO SIGNAL로 표시되고 루프는 16.32 FPS로 계속 돌았습니다.

## 2. 마주 오는 차의 ID 바뀜 원인

카메라 2대, seed 0의 프레임별 기록(측정, 트랙 예측, 속도)으로 찾았습니다. 예전 robust에서 원인은 네 가지였습니다.

1. 겹친 트랙 정리가 빠른 트랙을 지웠습니다. 18, 62, 107번째 프레임에서 속도 -21~-25 m/s로 잘 따라가던 트랙이, 같은 차로를 2 m/s로 가는 옆 차(정답 물체 1번) 트랙과 시선 방향 1.8m 안에 들어오자 짝짓기 거리 안에 겹친 트랙으로 판정되어 지워졌습니다. 남은 측정은 새 트랙 만들기 막기에 걸려 다음 프레임까지 트랙이 없었습니다.
2. 앞 카메라와 뒤 카메라 사이 공백이 트랙 유지 한도보다 깁니다. 앞 카메라가 마지막으로 본 자리는 x = 6.1m(68번째 프레임), 뒤 카메라가 처음 본 자리는 x = -4.4m(75번째 프레임)로 7프레임(0.47초) 비고, 예전 한도는 5프레임이었습니다. 속도 -24 m/s로 예측하면 75번째 프레임 예측 위치가 -5.1m로 측정과 0.7m 차이라 이어 붙일 수 있는 거리입니다.
3. 새 트랙의 속도가 늦게 붙습니다. 예측 오차의 0.1만 속도에 더하는 방식이라 50~57번째 프레임 속도가 0, -6.6, -1.0, 2.4, -1.4, -9.4, -12.1, -22.6 m/s로 8프레임 걸렸습니다. 그사이 측정이 예측에서 멀어져 놓치거나 다른 트랙에 붙었습니다.
4. 측정 잡음 가정이 먼 거리에서 좁습니다. 잡음 2화소 sim에서 잰 투영 오차 표준편차는 시선 방향으로 20m 안쪽 0.6~0.8m, 20~30m 2.15m, 30~40m 3.83m이고, 옆 방향은 0.3~0.5m였습니다. 예전 시선 방향 짝짓기 거리(35m에서 5.25m)는 1.4 표준편차라 먼 측정이 자주 빠졌습니다.

예측 단계의 dt는 원인이 아니었습니다. 이 평가에서 dt는 기준 카메라 시각 차이라 어긋남 0일 때 정확히 1/15초입니다. 앞뒤 카메라 경계의 투영점도 크게 튀지 않았습니다(뒤 카메라 첫 측정이 정답과 0.6m 차이).

이 sim의 마주 오는 차는 정답 물체 1번과 같은 차로(y = 3.5m)를 달려 그 차를 뚫고 지나갑니다. 두 차의 측정이 1m 안으로 겹치는 몇 프레임은 어느 추적기로도 가르기 어렵습니다. 이 차의 ID 바뀜을 상황별로 나누면 다음과 같습니다(seed 0~4 합, 원자료 out/measure/17/oncoming_causes.txt).

| 상황 | 카메라 2대 예전 / 새 | 카메라 4대 예전 / 새 |
|---|---|---|
| 1번 차와 겹침(x 차이 6m 안) | 31 / 25 | 29 / 18 |
| 앞뒤 카메라 넘어감(x 10m 안) | 25 / 1 | 7 / 0 |
| 먼 거리(x 25m 이상) | 13 / 4 | 16 / 3 |
| 그 밖 | 7 / 3 | 9 / 6 |

남은 바뀜은 대부분 겹치는 순간의 맞바뀜입니다.

## 3. 고친 추적기(robust)

`realityview/tracker.py`의 robust 판만 바꿨고 basic은 그대로입니다.

1. 트랙마다 칼만 필터를 둡니다. 상태는 위치와 속도, 측정 잡음은 시선 방향 hypot(0.5, 0.003 x 거리²)m, 옆 방향 0.5m로 2장에서 잰 값에 맞췄습니다. 등속 모델이 놓치는 가속도는 표준편차 4 m/s²로 둡니다.
2. 짝짓기 문턱은 마할라노비스 거리 제곱 13.8(자유도 2, 99.9%)이고, 옆 방향 차이 2.5m 제한은 그대로 둡니다. 옆 차선 차와 바뀌지 않게 하려는 것입니다.
3. 짝짓기는 헝가리안 방식(비용 = 마할라노비스 거리 제곱 + ln det S)입니다. 파이 .venv에 scipy가 없어 직접 구현했고, 시험에서 전수 탐색과 결과가 같습니다.
4. 새 트랙의 속도 불확실성은 앞뒤 15 m/s, 옆 3 m/s입니다. 앞뒤를 크게 두어 마주 오는 차 속도가 두세 프레임에 붙고, 옆을 작게 두어 처음 두 측정의 옆 잡음이 옆 속도 10 m/s로 바뀌던 것을 막습니다.
5. 속도가 자리 잡은 트랙(5번 넘게 짝지어진 것)은 10프레임까지 예측으로 남깁니다. 화면에는 예전처럼 놓친 지 1프레임 안의 트랙만 나옵니다.
6. 겹친 트랙 정리는 두 트랙 모두 속도가 자리 잡았고 속도 차이가 5 m/s를 넘으며, 그 차이가 속도 공분산에 견줘서도 뚜렷할 때(카이제곱 13.8) 합치지 않습니다.

하나씩 더하며 잰 값입니다(마주 오는 차 장면, seed 0~4, ID 바뀜 카메라 2대 / 4대).

| 단계 | 전체 | 마주 오는 차 |
|---|---|---|
| 예전 robust | 123 / 123 | 76 / 61 |
| 칼만, 헝가리안, 속도 5 m/s 정리 조건 | 104 / 64 | 57 / 27 |
| 옆 속도 3 m/s, 예측 유지 10프레임 추가 | 80 / 67 | 33 / 27 |
| 위에서 예측 유지만 뺌 | 104 / 66 | 57 / 27 |
| 정리 조건에 속도 공분산 추가(최종) | 76 / 55 | 33 / 27 |

예측 유지는 카메라 2대의 앞뒤 넘어감을 고쳤고, 카메라 4대에서는 측면 카메라가 공백을 메워 차이가 없었습니다.

## 4. 측면 카메라의 차 중심 추정

`project_detections(vehicle_center="box")`, `run_demo.py`와 `eval_tracking.py`의 `--vehicle-center box`로 넣었습니다. 기본은 예전과 같은 ray(시선 방향으로 차 길이 절반)입니다.

처음 가정(옆에서 보면 길이 절반 대신 폭 절반)으로는 지표가 거의 바뀌지 않았습니다. 잡음 없는 sim에서 카메라별 오차를 보니, 뒤쪽 옆을 보는 측면 카메라(yaw ±135도)에서 차 중심이 앞쪽(+x)으로 평균 1.26m 치우쳐 있었습니다. 박스 아래 끝은 차 바닥 네모 중 카메라 깊이가 가장 작은 점이라, 비스듬히 본 차에서는 중심까지 길이 절반이 아니라 "광축 방향으로 본 네모의 반폭"만큼 더 깊습니다. 그래서 차가 도로와 나란하다고 보고 카메라 광축 방향으로 중심 깊이를 구하도록 했습니다(`box_center`).

| 카메라 | 중심 오차 ray | 중심 오차 box |
|---|---|---|
| 왼쪽 측면 | 1.13m | 0.34m |
| 오른쪽 측면 | 0.99m | 0.34m |
| 전방 / 후방 | 0.33m / 0.47m | 0.34m / 0.52m |

조건은 카메라 4대 sim, 마주 오는 차 포함, 300프레임, 박스 잡음 없음, 사람 제외입니다. 두 카메라가 같은 차를 본 경우 두 투영점 사이 거리는 평균 1.04m에서 0.75m로 줄었습니다.

추적 지표는 기본 장면에서 seed별 값까지 그대로였고(카메라 4대 ID 바뀜 11, 중복 표시 55), 마주 오는 차 장면에서는 ID 바뀜이 카메라 4대 55회에서 67회, 2대 76회에서 84회로 늘었습니다. 늘어난 몫은 마주 오는 차와 1번 차가 겹치는 구간이라, 두 차 위치가 더 정확해져 겹치는 순간이 더 애매해진 것으로 보이지만 확인 필요입니다. 그래서 box는 옵션으로만 두었습니다.

카메라 4대 기본 장면의 남은 중복 표시는 차 투영 때문이 아니었습니다. 시각 맞춤 방식 seed 0~4의 중복 표시 100건 중 97건이 15m보다 먼 보행자(상대 12 m/s)에서 나왔습니다. 보행자는 투영점을 밀지 않으므로 이 옵션과 상관없고, 먼 거리 보행자의 중복은 남은 일입니다.

## 5. 카메라 끊김

`realityview/multicam.py`에 `ReconnectingSource`를 더했습니다. 안쪽 카메라의 read()가 None을 주면(USB 카메라는 2초 안에 새 프레임이 없을 때) 그 카메라를 신호 없음으로 두고, `--cam-retry`초마다 별도 스레드에서 다시 열어 한 장을 받아 보고 받으면 바꿔 끼웁니다. 열기와 닫기가 별도 스레드라 장치가 멈춰도 메인 루프는 처음 알아챌 때 한 번(2초)만 기다립니다. `FrameSyncer`에 "lost" 상태를 더해 그 칸은 NO SIGNAL 영상(OpenCV 글꼴에 한글이 없어 영어)이 되고, 끊기기 전 프레임은 hold로 다시 쓰지 않습니다. 검출은 그 칸에서 나오지 않으므로 추적은 나머지 카메라로 계속합니다. 기준 카메라가 끊기면 지금 시각을 기준으로 나머지 카메라를 묶습니다. 시간 맞춤을 쓰지 않는 경로도 같은 방식으로 NO SIGNAL 칸을 넣고 계속합니다. `--cam-retry`를 주지 않으면 예전처럼 카메라가 None을 줄 때 끝납니다.

가짜 소스 시험(`tests/test_tracking_fast.py`)은 가짜 VideoCapture를 쓴 실제 `UsbCameraSource` 스레드로, 20장 뒤 끊김, 다시 열기 두 번 실패(한 번에 0.2초 걸림), 세 번째 성공을 확인합니다. 끊긴 동안 read()가 0.15초 넘게 막힌 것은 처음 알아챌 때 한 번뿐이었습니다.

파이에서는 USB 카메라가 없어 `configs/four_cam_mixed.yaml`의 왼쪽 가짜 카메라만 `loop: false`로 바꾼 설정(파이 out/tmp/17_four_cam_drop.yaml)으로 확인했습니다. 파일 225장을 30fps로 읽으면 7.5초마다 끝나므로 그때마다 끊김이 됩니다. 전방, 후방은 CSI, Hailo 검출, `--sync --cam-retry 2 --tracker robust`, 20초입니다.

| 항목 | 값 | 비고 |
|---|---|---|
| 왼쪽 끊김 / 다시 열기 | 2회 / 2회 | 시도 2회 |
| 왼쪽 묶음 상태 | ok 145, hold 112, lost 70 | 묶음 327개 |
| 루프 | 16.32 FPS | 14 문서 같은 구성 15.84 FPS |

lost 70묶음은 끊길 때마다 2초 기다림과 다시 열기 시간을 합친 약 4.3초입니다. 이 실행에서 오른쪽 가짜 카메라는 ok 60, hold 267로 14 문서(ok 315)보다 hold가 많았고, 시각 차이 평균이 24.4ms로 허용 오차 25ms에 붙어 있었습니다. 가짜 카메라 도착 위상 차이로 보이지만 확인 필요입니다. Hailo 칩 온도는 실행 전 78.1도, 실행 뒤 84.3도였고 SoC는 56.5도에서 62.0도, throttled 0x0이었습니다. 원자료는 out/measure/17_pi_cam_retry.{log,json}, 17_pi_cam_retry_sync.csv, 17_pi_cam_retry_health.csv입니다.

쿼드 키트 칸은 장치 하나를 여러 칸이 나눠 쓰므로 `--cam-retry`로 감싸지 않습니다.

## 6. robust 기본값 추천

robust를 기본값으로 바꾸는 것을 추천합니다. 근거는 기본 장면과 마주 오는 차 장면, 카메라 2대와 4대의 네 조건 모두에서 basic보다 ID 바뀜이 8~44배 적고(381 대 20, 487 대 11, 608 대 76, 697 대 55), 물체당 트랙 수, 놓친 프레임 비율, 중복 표시도 모두 낮으며, 파이 CPU 비용이 물체 20개에서 6.6ms로 루프 시간(약 60ms)의 한 자리 퍼센트라는 점입니다. 다만 모든 수치가 sim(박스 잡음 정규분포 2화소, 5% 놓침)에서 나온 것이라, 바꾸기 전에 실제 주행 녹화 재생에서 basic과 robust의 화면을 한 번 견주어 보는 것을 조건으로 둡니다. 이번 작업에서 기본값은 바꾸지 않았습니다. `--vehicle-center box`는 기본값으로 추천하지 않습니다.
