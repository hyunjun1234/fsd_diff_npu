이 문서는 라즈베리파이 5(pi5)에서 지금 꽂힌 카메라 2대와 Hailo-8로 리얼리티 뷰 데모를 실제로 돌리고, 단계별 처리 시간을 잰 기록입니다. 측정일은 2026-11-24이고 구현 계획 4.2절의 앞부분에 해당합니다.

## 1. 측정 조건

| 항목 | 값 |
|---|---|

| 카메라 프레임레이트 | 두 대 모두 30 fps 요청 |

두 카메라는 책상 위에서 같은 방(사무실)을 보고 있고 차량에 달려 있지 않습니다. 그래서 탑뷰 영상 자체는 의미가 없고, 이번 측정은 처리 시간과 좌표 변환만 봅니다.

## 2. 설정과 코드 변경

- HEF: 파이의 `models/yolov8s_h8.hef`(/usr/share/hailo-models에서 복사)를 설정이 가리킵니다.
- 내부 파라미터: 데이터시트의 화소 크기와 렌즈 초점거리로 계산한 보정 전 근사값입니다. 전방 fx 761.9(수평 화각 53.5도), 후방 fx 564.3(수평 화각 68.5도)이고 계산 근거는 설정 파일 주석에 있습니다.
- 장착 높이와 각도: configs/two_cam.yaml 값을 그대로 옮겼고 실측이 필요합니다.
- 센서 모드: 두 카메라 모두 전체 화각을 2x2로 묶는 모드를 직접 고릅니다. 가운데만 잘라 쓰는 모드(ov5647 1920x1080, imx708 1536x864)가 뽑히면 화각이 설정과 달라지기 때문입니다. 실행 로그에서 두 모드가 실제로 선택된 것을 확인했습니다.
- imx708 Rotation 180: libcamera가 이미 보정해서 출력 영상은 바로 섰습니다. 그래서 설정의 rotation은 0입니다. 영상 속 명찰 글자가 바른 방향이라 거울상도 아닙니다. 다시 달아서 뒤집혀 보이면 rotation을 180으로 바꾸면 소스가 상하, 좌우를 함께 뒤집습니다.
- 전방 ov5647: 좌우 거울상 여부는 글자가 읽히지 않아 확인 필요입니다.
- PiCameraSource.close(): stop() 다음에 close()까지 불러 카메라를 놓아 주고, 설정 도중 실패해도 close()를 부릅니다.

파이 명령은 모두 파이 저장소 폴더(~/work/fsd_diff_npu)에서 .venv를 켠 뒤 실행했습니다.

## 4. 300프레임 실행 (기본 설정)

실행한 명령(파이):

```bash
timeout -s INT -k 10 180 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --headless --frames 330 --warmup 30 --profile --profile-out out/measure/01_profile_base.json --snapshot out/measure/01_snapshot_base.png
```

결과는 out/measure/01_profile_base.json, 01_profile_base.log, 01_snapshot_base.png에 있습니다.

330프레임 모두 오류 없이 돌았고, 앞 30프레임(첫 추론, 자동 노출 안정화)을 빼고 300프레임을 통계에 넣었습니다. 기본 점수 문턱 0.4와 주행 클래스(사람, 자전거, 차, 오토바이, 버스, 트럭)만 남기는 설정이라 이 방에서는 검출이 0개였습니다. 검출 경로 자체는 3장에서 확인했습니다.

| Hailo 추론 | 14.0 | 13.9 / 14.5 |
| NMS 파싱 | 0.1 미만 | 0.1 미만 |
| 검출 합계 | 17.6 | 17.3 / 19.3 |
| 지면 투영(IPM) | 0.1 미만 | 0.1 미만 |
| 병합 | 0.1 미만 | 0.1 미만 |
| 추적 | 0.1 미만 | 0.1 미만 |
| BEV 합성 | 23.0 | 22.7 / 23.7 |
| 렌더링 | 28.4 | 28.3 / 29.4 |
| 프레임 전체 | 70.6 | 70.2 / 72.9 |

- 전체 FPS는 워밍업 뒤 300프레임을 21.2초에 처리해 14.15 FPS입니다(벽시계 기준, 카메라 획득 포함).
- 카메라 획득 시간은 카메라 2대에서 다음 프레임을 받을 때까지 기다린 시간까지 포함합니다. 카메라가 30 fps로 앞서 찍어 두므로 기다림이 거의 없습니다.
- 전처리, Hailo 추론, NMS 파싱은 카메라 2대를 한 번에 처리한 값입니다. Hailo 추론은 2장 배치를 동기 호출로 넣고 받는 시간입니다.
- 검출 합계는 전처리, Hailo 추론, NMS 파싱의 합과 거의 같습니다(차이 0.1ms 미만).
- 지면 투영, 병합, 추적은 검출이 0개라 빈 입력 기준입니다. 물체가 있을 때 값은 5장의 sim 측정을 보십시오.
- 프레임 전체에서 CPU 몫(BEV 합성과 렌더링)이 51.4ms로 NPU 몫(17.6ms)의 약 3배입니다. 계획 3.3절의 예상대로 병목은 CPU입니다.

## 5. 물체가 있을 때 CPU 단계 (sim)

실제 방에 차와 사람이 없어서, 같은 설정 파일로 파이에서 sim 백엔드(합성 차량과 사람, 정답 박스에 잡음)를 돌려 투영, 병합, 추적 시간을 쟀습니다. 결과는 out/measure/01_profile_sim_cpu.json에 있습니다.

| 단계 | 평균 ms | p50 / p95 ms |
|---|---|---|
| 지면 투영(IPM) | 0.7 | 0.7 / 0.7 |
| 병합 | 0.1 미만 | 0.1 미만 / 0.1 |
| 추적 | 0.2 | 0.2 / 0.3 |
| BEV 합성 | 25.3 | 25.3 / 25.8 |
| 렌더링 | 77.1 | 82.7 / 89.3 |

조건: 카메라 2대 합성 영상, 300프레임, 합계 1463개 검출(프레임당 약 4.9개).

- 투영, 병합, 추적은 합쳐서 1ms 안팎이라 병목이 아닙니다.
- sim은 도로 마스크를 함께 내보내서 BEV 합성에 마스크 합성이, 렌더링에 도로 덧칠이 더해집니다.
- sim의 카메라 획득(163ms)은 합성 영상을 그리는 시간이라 실제 카메라와 비교하지 않습니다.

렌더링이 늘어난 원인을 보려고 같은 sim 장면에서 렌더링 함수만 도로 마스크 유무로 나눠 쟀습니다. 결과는 out/measure/01_render_road_split.log에 있습니다.

| 렌더링 입력 (sim, 50프레임) | 평균 ms | p50 / p95 ms |
|---|---|---|
| 탑뷰, 카메라 영상 모두 도로 덧칠 | 67.2 | 69.2 / 80.0 |
| 카메라 영상에만 도로 덧칠 | 61.9 | 64.0 / 72.7 |
| 도로 덧칠 없음 | 27.6 | 27.6 / 28.0 |

- 도로 덧칠이 없으면 27.6ms로 실제 카메라 기본 실행(28.4ms)과 같습니다.
- 늘어난 몫의 대부분(약 34ms)은 카메라 영상 2장 위의 도로 덧칠(render.py의 annotate_camera)이고, 탑뷰 도로 덧칠은 약 5ms입니다.
- 덧칠 시간은 도로로 칠할 화소 수에 따라 달라서, 장면이 움직이는 동안 값이 흔들렸습니다.
- 세그 HEF를 붙이면 기본 설정의 프레임 시간이 약 70ms에서 100ms 가까이로 늘어 10 FPS에 못 미칠 수 있습니다(확인 필요). 그때는 BEV 0.1m를 켜거나 카메라 영상 덧칠을 가볍게 바꿉니다.

## 6. 계획 3.3절 대응 비교

기본 설정이 이미 10 FPS를 넘었지만, 카메라 4대로 늘릴 때의 여유를 보려고 세 가지 대응을 모두 옵션으로 넣고 같은 조건(카메라 2대, Hailo-8, 330프레임 중 300프레임 측정)에서 한 번씩 돌렸습니다. 기본 동작은 바뀌지 않습니다.

| 실행 (옵션) | 화면 FPS | 프레임 전체 평균 / p95 ms |
|---|---|---|
| 기본 | 14.15 | 70.6 / 72.9 |
| BEV 0.1m (--bev-res 0.1) | 27.13 | 36.9 / 40.1 |
| 바닥 영상 끔 (--no-ground) | 30.00 | 33.3 / 34.1 |
| 렌더링 스레드 (--render-thread) | 19.81 | 50.5 / 55.4 |
| BEV 0.1m + 렌더링 스레드 | 30.01 | 33.3 / 35.4 |

같은 실행의 CPU 단계:

| 실행 | BEV 합성 평균 ms | 렌더링 평균 ms |
|---|---|---|
| 기본 | 23.0 | 28.4 |
| BEV 0.1m | 9.4 | 8.1 |
| 바닥 영상 끔 | 0 (건너뜀) | 8.5 |
| 렌더링 스레드 | 27.2 | 46.5 (별도 스레드) |
| BEV 0.1m + 렌더링 스레드 | 9.4 | 21.9 (별도 스레드) |

- 화면 FPS는 워밍업 뒤 완성된 대시보드 수를 걸린 시간으로 나눈 값입니다. 모든 실행에서 렌더링 스레드가 버린 프레임은 0개라 루프 FPS와 같았습니다.
- 30 FPS 두 건은 카메라 프레임레이트(30 fps)에 걸린 값입니다. 이때 카메라 획득이 5~7ms로 늘어난 것이 다음 프레임을 기다린 시간입니다.
- 효과가 가장 큰 단일 대응은 바닥 영상 끔(14.15에서 30.00 FPS)이고, 바닥 영상을 남기면서 빠른 것은 BEV 0.1m(27.13 FPS)입니다. BEV 0.1m는 탑뷰 칸 수가 4분의 1이 되어 합성과 렌더링이 함께 줄었습니다.
- 렌더링 스레드는 단독으로 19.81 FPS에 그쳤습니다. 렌더링이 다른 단계와 CPU를 나눠 쓰며 28.4ms에서 46.5ms로 늘었고, 전처리와 BEV 합성도 함께 느려졌습니다. 화면은 한 프레임 늦게 그려집니다.
- 추천: 카메라 4대로 늘릴 때는 BEV 0.1m를 먼저 켭니다. 바닥 영상이 필요 없으면 바닥 영상 끔이 가장 가볍습니다.

상태 기록:

| 실행 | 시작 (throttled, 온도) | 끝 (throttled, 온도) |
|---|---|---|
| BEV 0.1m | 0x0, 57.6도 | 0x0, 60.9도 |
| 바닥 영상 끔 | 0x0, 60.9도 | 0x0, 59.8도 |
| 렌더링 스레드 | 0x0, 59.8도 | 0x0, 64.2도 |
| BEV 0.1m + 렌더링 스레드 | 0x0, 59.8도 | 0x0, 62.0도 |

각 실행은 약 10~21초라 장시간 발열은 이번 측정으로 알 수 없습니다(확인 필요).

## 9. 확인 필요

- 전방 ov5647 렌즈: 영상에서 천장 경계선이 휘는 통 왜곡이 보이고, 같은 의자가 후방 imx708보다 작게 찍혔습니다. 실제 화각이 설정값 53.5도보다 넓을 가능성이 커서, 보정 전에는 전방 거리 값을 믿을 수 없습니다.
- 후방 imx708이 일반형인지 광각형인지: rpicam 이름이 imx708_wide가 아니라 일반형으로 봤지만 보정으로 확인해야 합니다.
- 카메라 프레임 지연: 루프가 카메라보다 느리면 Picamera2가 쌓아 둔 프레임을 받으므로 화면이 실제보다 늦을 수 있습니다. 지연 시간은 재지 않았습니다.
- 세그 HEF를 붙였을 때의 실제 렌더링 시간(5장은 sim 마스크 기준).
- 창을 띄우거나(--headless 없이) 동영상을 저장할 때의 FPS.
- 사람이나 차가 실제로 보일 때의 주행 클래스 검출 품질.

## 10. 사람이 할 일

1. 카메라 구성 결정: 계획(Camera Module 3 Wide 2대)대로 바꿀지, 지금 카메라로 갈지 정합니다. 바꾸면 이 문서의 측정을 다시 합니다.
2. 전방 ov5647 렌즈 사양 확인: 판매처 사양에서 렌즈 초점거리와 화각을 확인하고, 영상이 좌우 거울상인지 글자를 비춰 확인합니다.
3. 내부 보정: 데모와 같은 해상도, 같은 센서 모드로 체커보드 사진을 카메라마다 15장 이상 찍고 보정합니다. 전방은 통 왜곡이 보이므로 pinhole과 fisheye를 둘 다 돌려 RMS가 작은 쪽을 씁니다. 목표는 RMS 1px 이하입니다.
4. 장착과 외부 보정: 차량(또는 시험대)에 카메라를 달고 바닥에서 렌즈까지 높이, 숙인 각도, 좌우 위치를 줄자와 각도계로 잽니다. 바닥에 줄자로 잰 점을 찍어 외부 보정을 돌립니다. 목표는 지면 역투영 오차 10cm 이내입니다.
5. 거리 오차 측정: 줄자로 잰 5m 안쪽 위치에 차량이나 사람을 세우고 탑뷰 위치와 비교합니다. 목표는 0.5m 이하입니다.

체커보드 촬영 명령 예시입니다(파이에서 실행, 이번에 돌려 보지 않아 확인 필요). 40초 동안 2초마다 한 장씩 찍고 out/calib/front, out/calib/rear에 저장합니다. imx708은 초점을 주행 때와 같게 둡니다.

```bash
mkdir -p out/calib/front out/calib/rear
timeout 60 rpicam-still --camera 0 --mode 1296:972:10 --width 768 --height 576 -n --timelapse 2000 -t 40000 -o out/calib/front/img_%03d.jpg
timeout 60 rpicam-still --camera 1 --mode 2304:1296:10 --width 768 --height 432 -n --timelapse 2000 -t 40000 -o out/calib/rear/img_%03d.jpg
```

보정 명령입니다(파이 .venv). 결과 값은 화면에 나오며 configs/two_cam_current.yaml의 intrinsics에 붙여 넣습니다.

```bash
python3 scripts/calib_intrinsics.py --images "out/calib/front/*.jpg" --cols 9 --rows 6 --square 0.025 --model pinhole
python3 scripts/calib_intrinsics.py --images "out/calib/front/*.jpg" --cols 9 --rows 6 --square 0.025 --model fisheye
python3 scripts/calib_intrinsics.py --images "out/calib/rear/*.jpg" --cols 9 --rows 6 --square 0.025 --model pinhole
```

--cols, --rows는 체커보드 내부 코너 수, --square는 칸 한 변 길이(m)이므로 실제 보드에 맞춰 바꿉니다. 외부 보정은 scripts/calib_extrinsics.py --config configs/two_cam_current.yaml --camera front --points out/calib/front_points.csv로 돌립니다. 바닥에 점을 6개 이상 표시하고, CSV에 헤더 u,v,X,Y로 영상 픽셀 좌표와 줄자로 잰 차량 좌표(X 전방, Y 좌측, m)를 적습니다. 후방은 --camera rear로 같은 일을 합니다.
- 장시간(30분 이상) 실행 때의 온도와 스로틀링.
