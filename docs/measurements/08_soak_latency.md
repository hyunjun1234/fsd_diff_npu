# 안정성과 지연 시간 측정 기록

이 문서는 카메라 보정 없이 파이에서 잴 수 있는 세 가지, 즉 Hailo 검출 데모의 30분 연속 실행, 센서 타임스탬프 기준 화면 지연, 결과 화면 녹화의 비용을 잰 기록입니다. 측정일은 2026-11-24, 장치는 파이 5(4GB), Hailo-8(yolov8s_h8.hef), DX-M1(bisenetv2_1024x2048.dxnn), 설정은 configs/two_cam_current.yaml(전방 ov5647 768x576, 후방 imx708 768x432, 두 카메라 30fps 요청)입니다. 모두 창 없는 실행이고, 방 안이라 주행 클래스 검출은 0개입니다. 카메라 보정 전이라 거리 값은 보지 않았습니다.

## 요약

## 1. 30분 연속 실행 (Hailo 단독)

### 1.1 실행 방법

`--duration 1800`으로 30분 뒤 스스로 끝나게 하고, 바깥에 `timeout -s INT -k 10 2000`을 걸었습니다. ssh가 끊겨도 계속 돌도록 `nohup setsid`로 띄웠습니다. `--health-csv`는 1분마다 직전 1분의 FPS, throttled, SoC 온도, 프로세스 RSS, 시스템 MemAvailable을 한 줄씩 씁니다. `--profile`은 프레임마다 값을 쌓아 메모리가 늘어나므로 끄고 돌렸습니다. 결과는 out/measure/08_soak.csv, 08_soak.log에 있습니다.

```bash
timeout -s INT -k 10 2000 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --headless --duration 1800 --health-csv out/measure/08_soak.csv
```

### 1.2 결과

30분을 채우지 못했습니다. 720초째에 HailoRT의 장치 감시 기능이 Hailo-8 칩 온도 119.3도와 120.0도(센서 두 개)를 보고 "red zone"으로 스트림을 닫았고, 그다음 추론 결과가 깨져 `pyhailort`의 NMS 변환에서 IndexError로 끝났습니다(종료 코드 1). 같은 시각 파이의 throttled는 0x0이라 파이 쪽 전원이나 SoC 과열은 아닙니다.

| 경과 시간 | 1분 FPS | RSS MB |
|---|---|---|
| 1분 | 26.29 | 279.8 |
| 2분 | 25.65 | 279.9 |
| 3분 | 24.91 | 279.9 |
| 4분 | 24.49 | 279.9 |
| 5분 | 23.41 | 279.9 |
| 6분 | 23.03 | 279.9 |
| 7분 | 21.46 | 279.9 |
| 8분부터 12분 | 21.23 ~ 21.46 | 279.9 |

같은 기간 SoC 온도는 63.7~67.5도, MemAvailable은 2512MB 안팎으로 일정했습니다. 시작 줄의 RSS 268.8MB는 첫 추론 전 값입니다.

연속 실행은 3장의 녹화 시험(Hailo 단독 62초 두 번, 약 2분 30초 부하)이 끝나고 약 10초 뒤에 시작했습니다. 그래서 Hailo-8이 식지 않은 상태에서 시작했고, 아래 76초는 이 조건의 값입니다. HailoRT 경고가 나온 시점은 로그의 프레임 번호와 csv의 1분 프레임 수로 거꾸로 계산했습니다.

| 시점 (대략) | HailoRT 메시지 | 칩 온도 |
|---|---|---|
| 76초 | orange zone, CPU ECC error event | 103.7 / 104.0도 |
| 77초 | 클럭 400에서 350MHz | 기록 없음 |
| 133초 | 클럭 350에서 300MHz | 기록 없음 |
| 227초 | 클럭 300에서 250MHz | 기록 없음 |
| 354초 | 클럭 250에서 200MHz | 기록 없음 |
| 720초 | red zone, 스트림 닫음 | 119.3 / 120.0도 |

FPS가 시간에 따라 떨어진 것은 이 클럭 단계와 맞습니다. 메모리 누수 때문이 아니라 Hailo-8 열 보호 때문입니다. 시작 때 Hailo-8 온도는 재지 않아 확인 필요입니다. 같은 날 앞서 돌린 짧은 실행(60초 이하) 네 번의 로그에는 HailoRT 경고가 없었습니다.

메모리는 2분부터 멈출 때까지 10분 동안 RSS가 279.9MB에서 변하지 않아 새는 모습이 없습니다. 다만 12분 기록이라 30분 기준 판정은 확인 필요입니다.

dmesg(sudo 없이 읽힘, kernel.dmesg_restrict=0)에서 실행 시작(uptime 369605초) 뒤 줄은 카메라 링크 속도 두 줄뿐이었고 PCIe, AER, hailo 오류는 없었습니다. 부팅 이후 전체에도 AER은 부팅 때 "enabled" 두 줄뿐입니다. HailoRT의 "CPU ECC error event"는 칩 안 메모리 이야기이고 커널 로그에는 남지 않았습니다.

### 1.3 멈춘 뒤 온도

멈추고 1~2분 뒤 Hailo-8은 부하 없이 110.2도, DX-M1은 부하 없이 85도였습니다. DX-M1은 이번 연속 실행에서 쓰지 않았는데도 80도를 넘었으므로, 옆의 Hailo-8 열을 받는 것으로 봅니다. 식는 과정은 out/measure/08_cooldown.log에 1분마다 남겼습니다.

| 멈춘 뒤 (약) | Hailo-8 | DX-M1 |
|---|---|---|
| 2분 | 107.1도 | 85도 |
| 4분 | 98.2도 | 83도 |
| 7분 | 90.7도 | 80도 |
| 12분 | 84.0도 | 76도 |

10분 뒤에도 Hailo-8은 84도까지만 내려왔고 그때도 1분에 약 1도씩 내려가는 중이었습니다. 부하 없을 때의 안정 온도는 확인 필요입니다. 그 뒤 새로 넣은 칩 온도 열을 확인하려고 Hailo 단독으로 20초만 돌렸습니다(out/measure/08_hailo_temp_check.csv, 5초 간격). 시작 83.8도에서 20초 뒤 88.5도로 4초에 약 1도씩 올랐고, FPS는 26.0~26.2로 온도를 읽어도 줄지 않았습니다. 이 속도는 연속 실행 76초째에 orange zone(약 104도)에 닿은 것과 어긋나지 않지만, 연속 실행 시작 온도는 재지 않아 확인 필요입니다. 클럭을 200MHz까지 낮춘 뒤에도 104도에서 120도까지 계속 올랐으므로, 식은 상태에서 시작해도 멈추는 시점이 늦어질 뿐 30분은 어렵다고 봅니다.

### 1.4 판정과 대응

0단계의 "Hailo 30분 연속" 기준은 지금 방열 상태로는 통과하지 못합니다. DX-M1과 마찬가지로 Hailo-8에도 방열판이나 팬이 필요합니다. 방열을 바꾼 뒤 같은 명령에 아래 두 옵션을 더해 다시 돌립니다. `--health-csv`에 Hailo 백엔드면 칩 온도 열(hailo_temp_c)이 자동으로 붙고, `--hailo-stop-temp 95`는 그 값이 95도 이상이면 스스로 끝냅니다(HailoRT의 orange zone이 약 104도라 그 아래로 잡았습니다). 온도는 csv 줄을 쓸 때만 읽으므로, 이번처럼 1분에 10도 넘게 오르면 60초 간격으로는 95도를 넘겨 멈출 수 있습니다. 처음 다시 돌릴 때는 `--health-interval 10`을 권합니다.

```bash
timeout -s INT -k 10 2000 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --headless --duration 1800 --health-csv out/measure/08_soak2.csv --hailo-stop-temp 95
```

## 2. 센서 타임스탬프에서 화면 완성까지의 지연

### 2.1 재는 방법

`--profile`을 켜면 카메라에서 영상과 메타데이터를 같은 요청(`capture_request()`)에서 받아 SensorTimestamp를 꺼내고, `pipe.step()`이 대시보드를 돌려준 직후의 시각과 비교합니다. 녹화나 화면 표시는 이 시각 뒤라 들어가지 않습니다. `capture_metadata()`를 따로 부르면 다른 프레임의 값이 나오기 때문에 이렇게 했습니다.

SensorTimestamp와 `time.monotonic_ns()`가 같은 시계인지 카메라 1번에서 8프레임으로 확인했습니다. 차이가 10~29ms로 작고 양수였고, CLOCK_BOOTTIME과 CLOCK_MONOTONIC의 차이는 0이었습니다(파이가 잠든 적이 없어서). SensorTimestamp가 노출 시작인지 읽기 시작인지는 libcamera 문서로 확인하지 않아 확인 필요이고, 노출 시간은 약 12ms였습니다.

카메라 2대를 차례로 읽으므로 카메라마다 따로 모았고, "오래된 쪽"은 그 프레임에 쓴 두 영상 중 더 오래된 영상 기준입니다. 렌더링 스레드 모드(`--render-thread`)에서는 돌려받은 화면이 그 프레임 것이 아니라서 재지 않습니다.

실행한 명령(파이 저장소 폴더, .venv)은 아래와 같고, 결과는 out/measure/08_lat_hailo.json과 08_lat_dual.json(같은 이름의 .log)에 있습니다.

```bash
timeout -s INT -k 10 120 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --headless --frames 430 --warmup 30 --profile --profile-out out/measure/08_lat_hailo.json
timeout -s INT -k 5 30 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --seg-npu dxm1 --headless --frames 280 --warmup 30 --profile --profile-out out/measure/08_lat_dual.json
```

### 2.2 결과

Hailo 단독, 앞 30프레임을 뺀 400프레임, 루프 26.24 FPS입니다. 같은 실행의 throttled는 시작과 끝 모두 0x0, SoC 온도는 57.1도에서 63.7도였습니다.

| 기준 | 평균 ms | p50 / p95 ms |
|---|---|---|
| 전방 센서에서 화면 완성 | 80.1 | 79.1 / 96.9 |
| 후방 센서에서 화면 완성 | 76.2 | 75.6 / 92.7 |
| 오래된 쪽 카메라 기준 | 81.4 | 80.9 / 96.9 |
| 전방 센서에서 영상 받음 | 42.9 | 42.7 / 57.3 |
| 후방 센서에서 영상 받음 | 39.8 | 39.9 / 56.3 |

Hailo 검출 + DX-M1 세그(3프레임마다, 별도 스레드), 앞 30프레임을 뺀 250프레임, 루프 19.65 FPS입니다. throttled는 시작과 끝 모두 0x0이었습니다.

| 기준 | 평균 ms | p50 / p95 ms |
|---|---|---|
| 전방 센서에서 화면 완성 | 92.5 | 94.0 / 113.2 |
| 후방 센서에서 화면 완성 | 90.5 | 90.8 / 111.7 |
| 오래된 쪽 카메라 기준 | 93.8 | 95.4 / 114.3 |
| 전방 센서에서 영상 받음 | 42.8 | 42.3 / 58.4 |
| 세그 원본 영상에서 화면 완성 | 350.6 | 343.7 / 419.1 |

세그 마스크는 평균 5.1프레임, p95 6프레임, 최대 7프레임 묵은 것을 썼습니다. 세그 작업은 94번 넘겨 93번 끝났고 밀려 버린 것은 0번입니다. 마스크가 없던 4프레임은 첫 마스크가 나오기 전의 워밍업 구간입니다. 3프레임마다 넘기는데도 5프레임 넘게 묵는 것은 세그 한 번(카메라 2장)이 이 실행에서 평균 151.8ms로 이 루프의 3프레임(약 153ms)과 비슷하게 걸리기 때문입니다.

지연의 절반가량(약 40ms)은 처리 전 단계입니다. 센서 시각에서 `read()`가 영상을 돌려줄 때까지가 40~43ms인데, 노출과 전송을 빼면 루프(26 FPS)가 카메라(30fps)보다 느려 Picamera2 큐에 쌓인 앞 프레임을 받기 때문으로 봅니다(확인 필요). 카메라 프레임레이트를 루프 속도에 맞추거나 버퍼 수를 줄이면 이 몫이 줄 수 있습니다.

DX-M1 온도는 실행 전 75도, 실행 직후 81도였습니다(out/measure/08_dx_temp.log). 80도를 넘었으므로 그 뒤로는 DX-M1을 쓰는 실행을 하지 않았고, 약 2분 30초 뒤 다시 읽었을 때 78도였습니다.

## 3. 결과 화면 녹화

`--record-video 경로.mp4`를 주면 워밍업 뒤부터 대시보드를 동영상으로 저장합니다. 인코딩은 별도 스레드에서 하고, 코덱은 avc1(H.264, 파이 OpenCV 4.10의 FFmpeg libx264)을 먼저 쓰고 안 열리면 mp4v로 바꿉니다. 파일 fps는 `--record-fps`로 정하고, 주지 않으면 워밍업 동안의 루프 속도를 반올림해 씁니다. 루프 속도가 파일 fps와 달라도 들어온 시각에 맞춰 같은 영상을 반복하거나 건너뛰므로 재생 속도는 실제 시간과 같습니다.

같은 설정으로 녹화 없이, 녹화를 켜고 62초씩 이어서 돌렸습니다. 결과는 out/measure/08_rec_off.json, 08_rec_on.json에 있습니다.

```bash
timeout -s INT -k 10 120 python3 scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo --headless --warmup 30 --duration 62 --profile --profile-out out/measure/08_rec_on.json --record-video out/video/08_hailo_60s.mp4
```

| 실행 | 루프 FPS | 끝 SoC 온도 |
|---|---|---|
| 녹화 없음 | 26.23 | 65.3도 |
| 녹화 (avc1, 26fps 파일) | 21.30 | 67.5도 |

녹화를 켜면 FPS가 18.8% 떨어집니다. 이때 Hailo 추론은 13.9ms에서 15.5ms로 조금만 늘었고 프레임 전체가 38.1ms에서 46.9ms로 늘었으며, 로그에 HailoRT 경고가 없어 열 보호가 아니라 인코딩 스레드와 CPU를 나눠 쓴 몫으로 봅니다. 맥으로 받은 out/video/08_hailo_60s.mp4는 H.264, 1012x800, 26fps, 1582장, 60.85초, 735KB입니다(ffprobe). 루프가 21.3 FPS라 1297장이 들어갔고, 실제 시간에 맞추느라 일부 장이 반복되었습니다. 큐가 차서 버린 장은 없습니다. 대시보드 폭이 1013으로 홀수라 인코더가 1012로 한 줄을 잘랐습니다. 인코딩 스레드가 CPU를 나눠 쓰는 만큼 느려지므로, 길게 녹화할 때는 `--record-fps 10`처럼 낮추면 하락이 줄 것으로 봅니다(확인 필요).

## 4. 창을 띄운 FPS

파이에 모니터가 연결되어 있지 않습니다. `/sys/class/drm/card1-HDMI-A-1`과 `HDMI-A-2` 모두 disconnected이고, ssh 세션의 DISPLAY와 WAYLAND_DISPLAY는 비어 있습니다. 그래서 창을 띄운 FPS는 확인 필요로 남깁니다.
