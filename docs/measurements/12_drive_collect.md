# 12. 주행 수집 도구 시험 결과

이 문서는 차량 장착 전에 만든 주행 녹화, 트리거 클립, 섀도 실행 도구를 파이에서 시험한 결과입니다. 사용법은 docs/drive_recording.md 에 있습니다.

조건: 2026-11-25, 라즈베리파이 5(4GB), 카메라 2대(front ov5647 768x576 센서 1296x972, rear imx708 768x432 센서 2304x1296, 둘 다 30fps), configs/two_cam_current.yaml, 저장 장치는 SD 카드(시작 때 남은 공간 29.0GB). 장면은 사람과 차가 없는 실내라, 검출이 필요한 시험은 사람 사진 재생(out/replay/person, 카메라마다 사진 한 장)으로 했습니다. 카메라 보정 전이라 거리 값은 판정에 쓰지 않았습니다.

## 1. 주행 녹화 30초

```bash
timeout -s INT -k 15 60 python3 scripts/record_drive.py --config configs/two_cam_current.yaml \
    --name rec30 --duration 30 --segment 10 --status-interval 10
```

세그먼트 회전과 상태 기록이 시험 안에서 돌도록 둘 다 10초로 줄였습니다. 결과는 12_rec30.log, 12_rec30_drive.json, 12_rec30_status.csv 입니다.

| 항목 | front | rear |
|---|---|---|
| 프레임 | 893 | 893 |
| 누락(센서 시각 간격) | 0 | 0 |
| 영상 크기 | 36.7MB | 23.2MB |
| 프레임당 평균 | 41.1KB | 26.0KB |

30.3초 동안 회차 폴더 전체(csv, json 포함)가 60.1MB였고, 세그먼트 4개가 모두 segment.json과 함께 닫혔습니다. drive.json에는 센서 이름(ov5647, imx708)과 실제 센서 출력 크기, 설정 파일 본문, 시작과 끝의 SoC 온도와 throttled가 들어갔습니다. SoC는 54.6도에서 55.7도였습니다.

처음 만든 판은 읽기, JPEG 누르기, 쓰기를 한 스레드에서 했는데 같은 30초에 카메라마다 39장, 41장을 놓쳤습니다. 누락 위치가 세그먼트 경계 바로 뒤(0.2초에 6장, 1.1초에 33장)라 지난 세그먼트를 닫는 fsync가 SD 카드에서 길게 걸린 것으로 보고, 읽기와 쓰기 스레드를 나누고 닫기를 별도 스레드로 옮겼습니다. 그 뒤 위 결과처럼 누락이 0이 되었습니다. 그 판의 폴더는 파이의 out/drives/.old_test30_fsync_stall 에 남겨 두었습니다.

녹화 15초를 `time`으로 재면 CPU 시간이 5.7초(user 4.9, sys 0.8), 실제 시간 17.3초(시작과 종료 포함)였습니다. 코어 하나의 약 3분의 1입니다.

## 2. 한 시간 녹화에 필요한 공간

30초 결과 60.1MB / 30.3초 = 초당 1.98MB이므로 한 시간에 약 7.1GB입니다(카메라 2대, 위 해상도, 30fps, JPEG 품질 85, 실내 정지 장면). front만 4.4GB, rear만 2.8GB입니다.

지금 SD 카드의 남은 29GB에서 기본 멈춤 기준 5GB를 빼면 약 3.3시간을 녹화할 수 있습니다. 도로 장면은 영상이 복잡해 JPEG가 커지고, 카메라 4대면 두 배 안팎이 될 것으로 보지만 둘 다 확인 필요입니다. 차에서 몇 시간씩 모으려면 USB나 NVMe SSD를 쓰는 편이 낫습니다.

## 3. 안전 종료와 재생

`timeout -s TERM 12`로 SIGTERM을 보내 끊었습니다(12_rec_term.log, 12_term12_drive.json). 끝난 이유가 signal:SIGTERM으로 남았고, 5초 세그먼트 3개가 모두 닫혔으며, 카메라와 세그먼트마다 csv 줄 수와 실제로 풀리는 JPEG 수가 같았습니다(142, 150, 25장).

녹화한 회차 폴더를 그대로 `--replay`에 넣어 Hailo로 200프레임을 돌렸습니다(12_replay.log, 12_replay_health.csv). 25.6 FPS로 끝까지 돌았고 검출은 없었습니다(빈 방). 트리거 클립 폴더도 같은 방법으로 읽혔습니다(카메라마다 54장, 크기 768x576, 768x432).

## 4. 트리거 클립

| 실행 | 결과 | FPS |
|---|---|---|
| 실시간 카메라 20초, Hailo | 트리거 0건 | 25.78 |
| 사람 사진 재생 15초, Hailo | 클립 3개, 37MB | 25.8 |
| 사람 사진 재생 10초, Hailo와 DX-M1 섀도 | 클립 2개, 18MB | 20.48 |

실시간 실행은 빈 방이라 트리거가 하나도 나오지 않았습니다. 같은 조건에서 트리거 없이 잰 예전 값(out/measure/08_soak_latency.md 26.24 FPS)과 비슷했고, 링 버퍼 때문에 RSS가 270MB에서 370MB로 늘었습니다(12_trig_live_health.csv).

사람 사진 재생에서는 front 영상의 사람 상자 점수 0.371이 애매한 점수(0.3 이상 0.5 미만)로 잡혔습니다. 이 상자는 npu.score_thr 0.4보다 낮아 화면과 추적에는 가지 않는 상자입니다. 쿨다운 5초로 ambiguous 3건, track_new 1건이 클립을 만들었고 같은 종류 반복은 ambiguous 385건, track_new 5건이 막혔습니다. 첫 클립에는 두 트리거가 합쳐졌습니다. 클립 길이는 앞 2초와 뒤 2초로 약 105프레임이었고, 실행 시작 직후 클립은 앞쪽 버퍼가 덜 차 54프레임이었습니다. trigger.json 사본은 12_trigger_*.json 입니다.

track_new 6건(1건 저장, 5건 막힘)은 화면의 트랙 6개가 시작 직후 처음 ID를 받은 것과 수가 같습니다. 정지 장면에서 ID가 새로 바뀐 것은 아닌 것으로 봅니다.

사람 사진 재생 15초 동안 RSS가 230MB에서 711MB로 늘었습니다(12_trig_replay_health.csv). 링 버퍼(약 120MB)에 더해, 모으는 중인 클립과 저장을 기다리는 클립이 원본 프레임을 들고 있기 때문입니다. 클립 하나가 4초, 카메라 2대면 약 240MB입니다. 실행이 끝날 때 MemAvailable은 2060MB였습니다. 카메라 4대에서는 --trigger-pre, --trigger-post를 줄이거나 메모리를 다시 재야 합니다(확인 필요).

섀도 실행과 같이 돌린 10초에서는 npu_mismatch 트리거가 ambiguous 클립에 합쳐져 두 클립 모두에 들어갔습니다(12_shadow_trig.log).

Hailo HEF의 낮은 점수 한계를 보려고 같은 사진을 문턱 0으로 돌렸더니 상자 11개 중 최저 점수가 0.207이었습니다(12_hailo_score_floor.log). HEF 안의 NMS 문턱이 약 0.2로 보이므로 0.3 하한은 그대로 볼 수 있습니다. 정확한 문턱 값은 확인 필요입니다.

## 5. 섀도 실행

Hailo-8 기본(0회차 yolov8s_h8.hef), DX-M1 섀도(0회차 yolov8-s_640x640_ppu.dxnn), 사람 사진 재생 15초입니다(12_shadow_replay.log, 12_shadow_replay.csv, 12_shadow_replay.json).

| 항목 | 값 |
|---|---|
| 비교 프레임 | 306 (카메라 2대) |
| 짝지은 상자 | 1836 |
| 섀도가 놓친 상자 | 0 |
| 섀도만 찾은 상자 | 306 (front에서 프레임마다 1개) |
| IoU 평균, 최저 | 0.967, 0.946 |
| 점수 차이 평균(섀도 - 기본) | +0.004 |
| 섀도 추론 평균 | 26.4ms |
| 루프 FPS | 20.48 |

정지 사진이라 프레임마다 같은 결과가 되풀이되었습니다. 섀도만 찾은 1개는 같은 사진에서 DX-M1 쪽 점수만 0.4를 넘은 상자로 보이며, 어떤 상자인지는 확인 필요입니다. 섀도를 켜면 프레임마다 두 NPU가 모두 끝나기를 기다리므로, 같은 사진을 Hailo만으로 재생한 실행(25.8 FPS, 트리거 클립 켬)보다 약 21% 낮았습니다.

## 6. 온도

| 시점 | DX-M1 | Hailo-8 |
|---|---|---|
| 트리거 실시간 실행 전 | - | 77.8도 |
| 트리거 재생 실행 시작 | - | 81.0도 |
| 섀도 15초 전, 후 | 73도, 77도 | 82.5도, 84.5도 |
| 섀도와 트리거 10초 전, 후 | 75도, 78도 | 82.9도(시작 줄) |

DX-M1은 80도를 넘지 않았고, Hailo-8은 실행 시작 때 85도를 넘은 적이 없었습니다. 녹화 재생 실행(3절), 트리거 재생 실행, 섀도와 트리거 실행 앞에는 scripts/hailo_temp.py로 따로 읽지 않았고 표의 값은 각 실행 health csv의 시작 줄입니다(녹화 재생 77.9도). 섀도 시험은 `--backend hailo` 쪽만 했고 `--backend dxm1 --shadow`는 돌리지 않았습니다. 로그는 12_dx_temp.log, 12_hailo_temp.log, 각 실행의 *_health.csv 입니다.
