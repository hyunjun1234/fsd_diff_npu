# 4단계 준비: BEVPool CPU 시간 측정

이 문서는 FlashOcc의 BEVPool(깊이 분포 x 이미지 특징을 BEV 격자로 모으는 연산)을 라즈베리파이 5 CPU에서 돌린 시간과, 4단계 목표 200ms 안에서 차지하는 몫을 정리한 기록입니다.

## 1. 결론

- C 구현(ctypes, OpenMP)이 카메라 4대에서 스레드 1개 평균 7.84ms, 스레드 4개 평균 2.73ms입니다(파이5, 2026-11-24, 무작위 입력).
- 4단계 한 사이클 200ms 가운데 BEVPool 몫은 스레드 1개 기준 p95 7.93ms로 약 4.0%, 스레드 4개 기준 p95 2.79ms로 약 1.4%입니다.
- NumPy만 쓰면 카메라 4대에서 약 110ms(사이클의 약 55%)라서 4단계 목표에 쓰기 어렵습니다. C 빌드가 실패한 경우의 예비 경로로만 둡니다.

## 2. 측정 조건

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-24 |
| 장치 | 라즈베리파이 5, Cortex-A76 4코어 |
| 소프트웨어 | Python 3.13.5, NumPy 2.2.4, gcc 14.2.0 |
| CPU 조절기 | ondemand |
| 온도 | D=88 측정 직후 59.8도, D=59 측정 때는 확인 필요 |
| 입력 | 256x704, 특징 1/16 해상도 16x44 |
| 깊이 구간 | 1m부터 0.5m 간격 88개 |
| 채널 | 64 |
| BEV 격자 | 100x100, 0.8m 셀 |
| 격자 범위 | x, y는 -40~40m, z는 -1~5.4m |
| 반복 | 구현마다 예열 3회 후 30회 |

- 깊이 확률과 특징은 무작위 값입니다. 시간은 값이 아니라 점 개수에 비례하므로 무작위 값으로 충분합니다.
- 카메라 배치는 실제 보정값이 아니라 nuScenes와 비슷하게 잡은 가상 배치입니다. 초점거리 560px(가로 화각 약 64도), 높이 1.6m, 수평 시선, 4대는 전방, 후방, 좌, 우, 2대는 전방과 후방입니다.
- 시간에는 매 프레임 하는 일(특징 순서 바꾸기, 출력 0으로 채우기, 누적)이 모두 들어 있습니다. 미리 계산(precompute)은 따로 적었습니다.
- 모든 빠른 구현은 기준 구현과의 최대 차이가 1.2e-6 이하였습니다.

격자 안에 남은 점과 셀 수는 다음과 같습니다(가상 배치 기준).

| 조건 | 남은 점 | 점이 있는 셀 |
|---|---|---|
| 카메라 4대 | 148,984 / 247,808 | 5,861 / 10,000 |
| 카메라 2대 | 74,272 / 123,904 | 2,906 / 10,000 |

- 스레드 수는 C 구현에만 영향이 있습니다. reduceat, bincount, 기준 구현은 BLAS를 쓰지 않고 스레드 1개로만 돌아서 1개와 4개의 차이가 측정 오차 수준입니다.
- C 구현은 OpenMP로 빌드되었고 4개를 요청했을 때 실제로 4개가 돌았습니다. 카메라 4대에서 4스레드가 1스레드보다 약 2.9배 빠릅니다.
- 4스레드 값은 쉬지 않고 연달아 부른 결과입니다. 실제 파이프라인처럼 약 200ms마다 부르면 쉬던 스레드를 깨우는 시간이 더해질 수 있어 확인 필요입니다.

### 3.6 모델 선정 문서의 D=59 추정과 비교

모델 선정 문서 3장은 깊이 구간 59개(1~60m, 1m 간격)로 "수 ms"를 예상했습니다. 같은 조건(카메라 4대)을 따로 쟀습니다.

| 구현 | 스레드 1개 평균 ms | 스레드 4개 평균 ms |
|---|---|---|
| C | 4.50 | 1.98 |
| bincount | 53.92 | 53.86 |

D=59에서는 40m 격자 밖으로 나가는 점이 많아(75,460 / 166,144만 남음) D=88보다 빠릅니다. C 구현으로는 문서의 "수 ms" 예상이 맞았고, NumPy만으로는 맞지 않았습니다.

## 4. 4단계 목표에서 BEVPool 몫

4단계 목표는 카메라 4대 5 FPS, 한 사이클 200ms입니다(구현 계획 4.6절).

| 기준 | 카메라 4대 p95 | 200ms 중 비율 |
|---|---|---|
| C, 스레드 1개 | 7.93ms | 약 4.0% |
| C, 스레드 4개 | 2.79ms | 약 1.4% |
| NumPy bincount | 111.07ms | 약 55.5% |
| NumPy reduceat | 116.03ms | 약 58.0% |

- 실제 실행에서는 카메라 읽기, 렌더링, NPU 대기 스레드가 CPU를 함께 쓰므로 스레드 1개 값(약 8ms, 4%)을 계획값으로 잡기를 권합니다. 이 경우 NPU 두 모델과 나머지 CPU 일에 약 192ms가 남습니다.
- 실제 카메라 배치에서 격자 안에 남는 점이 늘면 시간도 비례해서 늡니다. 모든 점(247,808개)이 남는 최악의 경우 C 스레드 1개가 약 13ms일 것으로 보이며 확인 필요입니다.
- 학습된 FlashOcc의 실제 깊이 출력과 실제 카메라 보정값으로 잰 시간은 모델 파일이 없어 확인 필요입니다.

## 5. 모델을 붙일 때 확인할 것

- 셀 번호를 정할 때 이 구현은 floor를 씁니다. 원래 BEVDet/FlashOcc 코드는 정수 변환만 해서 아래쪽 경계 바로 밖의 점을 0번 셀에 넣는 것으로 알고 있으나 확인 필요입니다. 결과가 다르면 학습 코드 방식에 맞춥니다.
- 출력 순서는 (C, X, Y)입니다. FlashOcc BEV 인코더 ONNX의 입력 순서가 (C, Y, X)이면 전치가 필요합니다(확인 필요).
- cameras_to_arrays는 자르기 없이 크기만 바꿨다고 가정합니다. 학습 때 자르기(crop)를 썼다면 K의 cx, cy를 그만큼 옮겨야 합니다.

## 6. 참고: 맥에서 잰 값

맥(Apple Silicon, Python 3.9.6, NumPy 2.0.2, Apple clang, OpenMP 없음, 스레드 1개, 20회)에서 카메라 4대는 C 1.02ms, reduceat 16.74ms, bincount 52.50ms, 기준 66.95ms였습니다. 파이5보다 C가 약 8배 빠르므로 맥 값으로 파이 시간을 추정하면 안 됩니다.

## 7. 다시 재는 방법

맥의 저장소 폴더에서 실행합니다. 결과 JSON은 파이의 ~/work/fsd_diff_npu/out/measure/ 에 생기고, 마지막 rsync로 맥의 out/measure/ 로 받아 옵니다.

```
ssh -o BatchMode=yes -o ConnectTimeout=10 pi5 'cd ~/work/fsd_diff_npu && . ~/work/fsd_diff_npu/.venv/bin/activate && for t in 1 4; do timeout 400 python scripts/bench_bevpool.py --threads $t --reps 30 --out out/measure/04_bevpool_cpu_pi5_t$t.json; done'
ssh -o BatchMode=yes -o ConnectTimeout=10 pi5 'cd ~/work/fsd_diff_npu && . ~/work/fsd_diff_npu/.venv/bin/activate && for t in 1 4; do timeout 180 python scripts/bench_bevpool.py --threads $t --reps 30 --cams 4 --bins 1,60,1 --methods c,bincount --out out/measure/04_bevpool_cpu_pi5_d59_t$t.json; done'
rsync -av -e 'ssh -o BatchMode=yes -o ConnectTimeout=10' pi5:~/work/fsd_diff_npu/out/measure/ out/measure/
```

원본 기록은 out/measure/04_bevpool_cpu_pi5_t1.json, 04_bevpool_cpu_pi5_t4.json, 04_bevpool_cpu_pi5_d59_t1.json, 04_bevpool_cpu_pi5_d59_t4.json, 04_bevpool_cpu_mac_t1.json입니다.
