# 3D 화면에 차선과 신호등 색 더하기

이 문서는 3D 화면과 탑뷰에 차선 곡선과 신호등 색을 더한 작업의 결과와 측정 기록입니다. 측정일은 2026-11-25이고, 파이 측정은 파이 5, Hailo-8(HailoRT 4.23.0, yolov8s_h8.hef), configs/two_cam_current.yaml의 카메라 2대(전방 ov5647 768x576, 후방 imx708 768x432)로 했습니다. 카메라 보정 전이라 거리 값은 판정에 쓰지 않았습니다. DX-M1은 쓰지 않았습니다.

## 요약

| 항목 | 결과 | 조건 |
|---|---|---|
| 3D 화면 FPS(기준) | 20.88 | 파이, Hailo, `--view 3d`, 20초 |
| 3D + 차선 + 신호등 FPS | 19.66 | 파이, 같은 옵션에 `--lanes --traffic-lights`, 20초 |
| 프레임 전체 시간 | 47.7ms 대 50.6ms | 위 두 실행의 평균 |

목표인 15 FPS는 파이 실제 카메라 실행에서 10초 단위 기록 두 번 모두 19.58, 19.69 FPS로 넘었습니다(out/measure/15_pi_health_lanes.csv). 다만 실행 장소가 사무실이라 차선과 신호등이 없었고, 차선 검출 3.4ms와 신호등 0.0ms는 "찾을 것이 거의 없을 때" 값입니다. 도로에서는 차선 검출 8.1ms, 그리기 1.9ms, 신호등 0.9ms(합성 장면 파이 CPU 값)를 기준 47.7ms에 더하면 약 58.6ms, 17 FPS 안팎으로 예상합니다. 이 추정에는 물체 그리기 비용이 빠져 있습니다(10번 문서에서 3D 그리기가 물체 0개 11.1ms, 20개 23.4ms). 실제 도로 값은 확인 필요입니다.

## 1. 차선 모델이 아니라 고전 방식을 고른 이유

파이의 /usr/share/hailo-models와 저장소 models/에 있는 HEF는 yolov8s, yolov6n, yolov5n_seg, yolov8s_pose, resnet_v1_50, scrfd, yolox_s, yolov5s_personface 계열이고 차선 모델(ufld 계열)은 없었습니다. models/dxnn/에도 차선 모델이 없습니다. 새 모델을 받지 않는 조건이라 IPM 바닥 영상에서 CPU로 차선을 찾는 방식(realityview/lanes.py)을 만들었습니다.

실제 도로 사진은 저장소(git ls-files의 그림과 동영상)와 파이(20KB 넘는 jpg, png, mp4 전체, 녹화 폴더와 드론 데이터셋 제외 96개)에서 찾았지만 없었습니다. 파이에 있는 것은 이 저장소 문서 그림, 실내 NPU 검출 화면 캡처, 도구 예제 그림이었습니다(파일 이름과 폴더 기준, 내용 확인은 일부만). 그래서 정확도는 합성 장면으로만 쟀습니다.

## 2. 차선 검출

탑뷰 바닥 영상(5cm 칸)을 10cm 칸으로 줄인 뒤 아래 순서로 찾습니다.

1. 색 임계값: 밝기 170 이상이고 채도 70 이하면 흰색, 색상 12~38이고 채도 70 이상이면 노란색 후보입니다(OpenCV HSV).
2. 폭과 기울기: 가로 0.6m 커널 top-hat으로 주변보다 25 이상 밝은 좁은 띠만 남기고, 좌우 Sobel 기울기가 30 이상인 자리 근처만 남깁니다. 넓은 보도나 밝은 벽 면은 여기서 빠집니다.
3. 영역: 카메라가 보는 셀을 0.4m 깎아 경계선을 지우고, 도로 마스크가 있으면 0.3m 넓힌 마스크 안만 남깁니다. 넓히는 이유는 도로 가장자리 실선이 마스크 경계에 반쯤 걸치기 때문입니다.
4. 가림: 검출 상자 안 화소를 펴 놓은 탑뷰 자리를 뺍니다. 차체가 IPM에서 바닥으로 길게 늘어져 차선처럼 보이는 것을 막습니다. 상자가 없는 프레임은 이 합성을 건너뜁니다.
5. 출발점과 슬라이딩 윈도우: X -8~8m 띠의 열 히스토그램 봉우리를 출발점으로 잡고, X=0에서 앞뒤로 1m 윈도우(반폭 0.5m)를 옮기며 화소를 모읍니다. 차 옆 사각지대(x -2.1~2.8m)에서는 화소가 없어도 중심을 들고 넘어갑니다.
6. 곡선: 모은 화소로 Y = aX² + bX + c(차량 좌표, m)를 맞추고, 곡선에서 먼 화소를 빼고 한 번 더 맞춥니다. 화소가 있는 X 구간이 6m보다 짧으면 1차로 맞춥니다.
7. 실선/점선과 색: 곡선을 1m 칸으로 나눠 카메라가 보는 칸 중 화소가 있는 칸이 75% 이상이면 실선입니다. 보이는 칸이 9m(점선 한 주기)보다 짧으면 이번 프레임은 정하지 않습니다. 노란 화소가 40% 이상이면 노란 차선입니다.
8. 좌우: X=0 횡위치가 +2.6m 안에서 가장 가까운 것이 왼쪽 경계, -2.6m 안에서 가장 가까운 것이 오른쪽 경계, 나머지는 "그 밖"입니다.

프레임 사이에서는 LaneSmoother가 X=0 횡위치 0.7m 안의 곡선끼리 이어 붙이고, 계수를 0.35 비율로 지수 평활하며, 실선/점선과 색은 최근 9번 다수결로 정합니다. 5프레임까지 못 찾아도 지난 곡선을 보여 줍니다. 아직 실선/점선을 한 번도 정하지 못한 곡선은 실선으로 그립니다.

## 3. 신호등 색

`--traffic-lights`를 켜면 Hailo와 DX-M1 검출기가 남기는 클래스에 COCO traffic light(9)를 더합니다. 상자를 잘라 밝기 150 이상, 채도 90 이상인 켜진 화소를 색상으로 나눠 셉니다. 빨강은 색상 0~9와 160~180, 노랑은 10~34, 초록은 35~100입니다. 한 색이 켜진 화소의 60% 이상이면 그 색이고, 두 색이 비슷하면 켜진 등의 위치로 정합니다. 세로형은 위에서부터, 가로형은 왼쪽부터 빨강, 노랑, 초록 순서로 봅니다. 켜진 화소가 4개 미만이거나 상자 넓이의 2% 미만이면 모름입니다. 상자 짧은 변이 6px보다 작아도 모름입니다.

같은 카메라에서 상자 중심이 상자 긴 변 안에 있으면 같은 신호등으로 이어 붙이고, 최근 5프레임 다수결로 색을 정합니다. 3프레임까지 못 찾아도 지난 결과를 유지합니다.

신호등은 공중에 있어 상자 아랫변을 바닥으로 투영하면 틀립니다. 그래서 추적기와 탑뷰 물체에는 넣지 않고, 파이프라인은 옵션과 상관없이 traffic light 상자를 지면 투영에서 늘 뺍니다. 화면에는 두 가지로 그립니다. 하나는 화면 오른쪽 위(탑뷰는 왼쪽 위) 신호등 아이콘으로, 앞 카메라의 색을 아는 가장 큰 상자를 대표로 고릅니다. 다른 하나는 상자 방향으로 카메라에서 15m(장면 축척 곱함) 떨어진 자리에 세운 기둥과 상태 색 상자입니다. 기둥 거리는 표시용이고 실제 거리가 아닙니다.

## 4. 화면

3D 화면은 바닥 다음, 물체보다 먼저 차선을 그립니다. 내 차선(왼쪽과 오른쪽 경계 사이)은 반투명 파랑으로 칠하고, 차선은 흰색이나 노란색, 실선이나 점선(3m 칠하고 6m 비움)으로 그립니다. 점선 무늬의 위치는 실제 도로 점선과 맞추지 않은 표시용입니다. 차선은 바닥 캐시에 굽지 않아 `--view3d-ground-every`를 써도 매 프레임 새로 그립니다. 탑뷰도 같은 곡선과 내 차선을 그립니다.

| 파일 | 내용 |
|---|---|
| out/measure/15_sim_both.png | 맥 합성 장면, `--view both --lanes --traffic-lights --sim-curvature 0.006 --sim-lights` |
| out/measure/15_pi_sim_3d_lanes.png | 파이 합성 장면, `--view 3d`, 같은 옵션 |
| out/measure/15_pi_3d_lanes.png | 파이 실제 카메라(사무실), 차선과 신호등 없음 |

두 합성 장면 그림은 가림 처리와 "정하지 않음" 처리를 넣기 전 코드로 그렸습니다. 그리는 코드는 그 뒤로 바뀌지 않았습니다.

## 5. 합성 장면 정확도

sim.py에 두 옵션을 더했습니다. `curvature`는 도로를 Y = curvature/2 x X²로 굽히고(자차는 차로 가운데), `traffic_lights`는 앞쪽 18m에 세로형, 22m에 가로형 신호등을 띄우고 2초마다 색을 바꿉니다. 두 옵션 모두 끄면 영상과 검출 잡음이 예전과 똑같습니다(시험 test_sim_defaults_unchanged). 정답 차선은 점선 흰색 둘(±1.75m)과 실선 노란색 둘(±5.25m)입니다.

아래는 맥에서 `scripts/eval_lanes_lights.py`로 잰 값입니다. 장면에는 기본 물체 6개(차 4대, 트럭 1대, 보행자 1명)가 있고, 곡선 오차는 X 3~15m에서 잰 횡위치 차이의 평균입니다.

| 조건 | 찾은 비율 / 오차 평균 / 오차 p95 | 실선점선 / 색 / 신호등(판별, 다수결) |
|---|---|---|
| current, 곡률 0 | 0.968 / 0.013m / 0.039m | 1.00 / 1.00 / 0.995, 0.92 |
| current, 곡률 0.006 | 0.965 / 0.024m / 0.048m | 1.00 / 1.00 / 0.995, 0.92 |
| current, 곡률 -0.006 | 0.963 / 0.022m / 0.043m | 1.00 / 1.00 / 0.995, 0.92 |
| two_cam, 곡률 0 | 0.995 / 0.021m / 0.053m | 0.96 / 1.00 / 0.915, 0.91 |
| two_cam, 곡률 0.006 | 0.995 / 0.029m / 0.057m | 1.00 / 1.00 / 0.915, 0.91 |
| two_cam, 곡률 -0.006 | 0.995 / 0.030m / 0.060m | 0.98 / 1.00 / 0.915, 0.91 |

current는 configs/two_cam_current.yaml, two_cam은 configs/two_cam.yaml입니다. 결과 파일은 out/measure/15_eval_mac.json, 파이에서 같은 스크립트로 잰 값은 out/measure/15_eval_pi.json(current, 60프레임, 실선점선과 색 1.00, 신호등 판별 1.00)입니다.

신호등 다수결 정확도가 이번 프레임 판별보다 낮은 것은 색이 바뀔 때 다수결이 2~3프레임 늦게 따라가기 때문입니다. 깜빡임을 줄이는 대가입니다. two_cam 설정의 판별 정확도 0.915는 전방 카메라 화각이 넓어(fx 311) 22m 가로형 신호등 상자 짧은 변이 6px보다 작아져 모름이 나온 것으로 추정합니다(확인 필요).

가림 처리와 "정하지 않음" 처리를 넣기 전에는 current 설정에서 실선점선 정확도가 0.87, 곡률 0.006의 색 정확도가 0.94였습니다. 앞뒤 차가 내 차선 경계를 가려 보이는 구간이 4m 안쪽이 되면 점선 한 칸이 실선처럼 보였습니다(틀린 프레임의 보인 구간 5.0~8.8m 확인). 색이 노란색으로 바뀐 것은 주황색 트럭 차체가 IPM에 늘어진 탓으로 추정합니다(가림 처리 뒤 1.00이 되었지만 원인 자체는 확인 필요).

## 6. 파이 측정

차선 실행은 가림 처리를 넣은 뒤 한 번 더 했고, 첫 실행의 json, log, csv는 두 번째 실행 결과로 덮어썼습니다(첫 실행 19.79 FPS, 프레임 전체 50.3ms). 실행 전 Hailo 칩 온도는 77.8도, 81.9도, 79.9도였고(85도 이하라 기다리지 않음), 남은 기록의 최고는 84.4도입니다(out/measure/15_hailo_temp.log, 15_pi_health_*.csv). 덮어쓴 첫 실행 중 최고는 84.7도였습니다. SoC 온도는 56~63도, throttled는 0x0이었습니다. 각 실행은 `--duration 20 --warmup 30 --profile --health-interval 10 --hailo-stop-temp 95`입니다.

```
timeout -s INT -k 10 40 python scripts/run_demo.py --config configs/two_cam_current.yaml --backend hailo \
    --view 3d --lanes --traffic-lights --headless --duration 20 --profile \
    --profile-out out/measure/15_pi_3d_lanes.json --health-csv out/measure/15_pi_health_lanes.csv \
    --health-interval 10 --hailo-stop-temp 95
```

결과는 out/measure/15_pi_3d_lanes.json과 같은 이름의 .log에 생깁니다. 기준 실행은 `--lanes --traffic-lights` 없이 15_pi_3d_base.json에 있습니다.

| 단계 | 기준 평균 ms | 차선 + 신호등 평균 ms |
|---|---|---|
| Hailo 추론 | 14.0 | 13.9 |
| BEV 합성 | 9.2 | 9.0 |
| 차선 검출 | 없음 | 3.4 |
| 신호등 색 판별 | 없음 | 0.0 |
| 렌더링(3D 포함) | 18.9 | 18.7 |
| 3D 차선 그리기 | 없음 | 0.6 |
| 프레임 전체 | 47.7 | 50.6 |

사무실에서는 검출이 0개라 신호등 시간은 0이었고, 차선 검출 393번 중 평균 0.44개의 가짜 곡선이 나왔습니다. 바닥이나 가구의 밝은 가장자리가 원인으로 추정합니다(확인 필요). 내 차선 양쪽 경계를 찾은 프레임은 없었습니다(lane_light_stats).

파이 CPU에서 합성 장면으로 잰 값은 차선 검출 8.1ms(p95 8.9ms, 상자 가림 합성 포함), 신호등 2개 판별 0.9ms입니다(15_eval_pi.json). 같은 장면을 `--view 3d`로 그린 실행에서 3D 차선 그리기는 1.9ms였습니다(15_pi_sim_3d_lanes.json, 가림 처리 전 코드라 이 파일의 차선 검출 5.4ms는 가림 합성이 빠진 값입니다).

## 7. 남은 일

1. 실제 도로 영상으로 차선과 신호등을 확인해야 합니다. 지금 정확도는 모두 합성 장면 값이라 실제 노면 반사, 그림자, 닳은 차선, LED 신호등 깜빡임에서는 확인 필요입니다.
2. 실제 카메라 실행은 FPS와 추가 시간만 보여 줍니다. 실제 카메라로 차선이나 신호등을 본 적은 아직 없고, Hailo의 클래스 9가 traffic light로 이어지는 경로도 실제 출력으로는 확인 필요입니다.
3. 사무실에서 가짜 곡선이 평균 0.44개 나왔습니다. 도로 세그 마스크(DX-M1 BiSeNetV2, `--seg-npu dxm1`)와 같이 쓰면 도로 밖 화소가 빠지지만 이 조합은 재지 않았습니다(DX-M1 방열 전).
4. 신호등 아이콘과 기둥은 거리를 주장하지 않는 표시입니다. 기둥 15m는 고정값이라 카메라 보정 뒤에도 실제 거리를 쓰려면 신호등 높이 가정 같은 다른 근거가 필요합니다.
5. 가로형 신호등은 왼쪽부터 빨강, 노랑, 초록 순서로 봅니다. 국내 4색(좌회전 화살표 포함) 신호등은 위치 판단이 틀릴 수 있어 색 판별을 먼저 씁니다. 화살표 구분은 하지 않습니다.
6. `--shadow`와 `--traffic-lights`를 같이 쓰면 섀도 백엔드는 기본 클래스만 남기므로 신호등 상자가 두 NPU 불일치로 셀 수 있습니다(확인 필요).
7. 도로에서 15 FPS가 빠듯하면 `--lanes-every 2`로 차선 검출을 두 프레임에 한 번 하면 됩니다(기본 1).
