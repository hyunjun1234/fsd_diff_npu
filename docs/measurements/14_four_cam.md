# 카메라 4대 지원 사전 작업 결과

이 문서는 쿼드 키트와 USB 카메라 없이 지금 장비로 만든 카메라 4대 입력, 시간 맞춤, 합성 4대 재생, 파이 실측 결과를 정리한 기록입니다. 측정일은 2026-11-25이고, 파이는 Raspberry Pi 5 + Hailo-8(yolov8s_h8.hef), 맥은 맥북(파이썬 3.9)입니다. 카메라 보정 전이라 거리 값으로는 판정하지 않았습니다.

## 1. 요약

파이에서 CSI 2대와 가짜 측면 카메라 2대를 섞은 4대 구성으로 Hailo 검출을 돌렸을 때 15.84 FPS(시간 맞춤 켬)와 16.16 FPS(끔)가 나와 계획 4.4절의 4대 기준 8 FPS를 넘었습니다. 다만 측면 2대는 파일을 읽은 것이라 USB 전송 비용이 빠져 있고, 쿼드 키트의 프레임레이트 절반 제한도 들어가 있지 않습니다.

시뮬레이션에서는 시각 어긋남 0ms, 20ms, 50ms 사이의 추적 지표 차이가 seed 잡음 수준이었습니다. 이 장면의 물체가 대부분 상대 속도 1~2 m/s라 50ms 어긋나도 위치가 10cm 안쪽으로만 달라지기 때문입니다. 마주 오는 차(상대 25 m/s)를 넣으면 어긋남이 없어도 ID 바뀜이 크게 늘어, 빠른 물체 추적은 시간 맞춤과 별개로 고칠 일로 남았습니다.

## 2. 만든 것

코드는 `realityview/multicam.py`에 모았고, 설정에서 카메라마다 `source.type`으로 입력을 고릅니다. 기존 `picamera2`, `opencv` 동작은 그대로입니다.

| type | 쓰임 | 시각 |
|---|---|---|
| picamera2 | CSI 카메라 | 센서 시각(SensorTimestamp) |
| usb | USB UVC 카메라(OpenCV V4L2) | 받은 시각 - timestamp_offset_ms |
| video | 동영상 파일을 가짜 USB 카메라로 | 받은 시각 |
| quad | 쿼드 키트 2x2 프레임의 한 칸 | 합쳐진 프레임 시각, 지연 보정 |

USB 카메라는 별도 스레드가 계속 읽고 가장 최근 한 장만 들고 있으며, 받은 순간 `time.monotonic_ns()`를 붙입니다. Picamera2 센서 시각과 같은 시계라 두 종류를 같은 기준으로 비교할 수 있습니다. 받은 시각은 노출 시각보다 전송 시간만큼 늦으므로 그만큼을 `timestamp_offset_ms`로 뺄 수 있게 했고, 실제 값은 USB 카메라를 단 뒤 재야 합니다(확인 필요).

쿼드 키트 소스(`QuadSplitSource`)는 합쳐진 프레임을 루프마다 한 번만 읽고 네 칸으로 나눕니다. 칸마다 `lag_frames`를 적으면 `align: true`일 때 늦지 않은 칸을 이전 프레임에서 꺼내 네 칸이 같은 순간을 보이게 하고, `align: false`일 때는 칸은 그대로 두고 시각만 한 프레임 간격만큼 앞당깁니다. 칸 순서(왼쪽 위부터 0, 1, 2, 3)와 2번, 3번이 늦는 방향은 제품 설명만 보고 정한 것이라 실제 키트로 확인 필요입니다.

`FrameSyncer`는 기준 카메라 시각에 가장 가까운 프레임끼리 묶습니다. 허용 오차(기본 25ms) 안이면 ok, 넘으면 `hold`(가진 프레임 중 가장 가까운 것 재사용) 또는 `blank`(검은 빈 칸)입니다. 묶음마다 카메라별 시각 차이를 csv(`--sync-csv`)와 요약으로 남깁니다. `--skew-comp`를 주면 그 차이만큼 물체 위치를 가장 가까운 트랙의 속도로 옮겨 추적기에 넣습니다. 둘 다 `run_demo.py`의 옵션이며 기본은 꺼져 있습니다.

## 3. 파이의 USB 카메라 확인

`v4l2-ctl --list-devices`와 `lsusb`로 확인한 결과 USB 카메라는 꽂혀 있지 않습니다(USB에는 키보드 수신기만 있음). `/dev/video0`~`/dev/video15`는 CSI 장치(rp1-cfe)라서, `configs/four_cam.yaml`의 좌우 `opencv, uri: 0/1`을 파이에서 그대로 쓰면 USB 카메라가 아니라 CSI 노드를 엽니다. USB 카메라는 `/dev/v4l/by-id/...` 경로로 적어야 합니다. 그래서 USB 소스는 가짜 VideoCapture와 동영상 파일로 시험했습니다(`tests/test_four_cam.py`).

## 4. 합성 4대 장면 재생(맥)

`scripts/make_sim4.py`로 `configs/four_cam.yaml` 4대 장면을 15fps, 225프레임으로 만들었습니다. 왼쪽 카메라는 20ms, 오른쪽은 50ms 늦게 찍고(흔들림 표준편차 1ms), 오른쪽은 5% 확률로 프레임을 빠뜨렸습니다(225장 중 218장). 결과는 `out/sim4/cam0~3.mp4`, `cam0~3.csv`, `gt.json`입니다.

이 폴더를 `--replay out/sim4 --backend gt --view both --tracker robust`로 넣으면 시간 맞춤이 자동으로 켜지고, 탑뷰와 3D 화면, 추적이 4대 모두에서 돌았습니다(`out/measure/14_sim4_replay_snapshot.png`, 영상 `out/video/14_sim4_replay.mp4`). 맥에서 화면 그리기까지 43.8 FPS였고 검출은 정답 상자라 NPU 시간은 없습니다.

| 카메라 | 묶은 뒤 차이 평균, 최대 | ok / hold / blank |
|---|---|---|
| 왼쪽(20ms 어긋남) | 20.0ms, 23.1ms | 225 / 0 / 0 |
| 오른쪽(50ms, 5% 누락) | 18.8ms, 84.6ms | 217 / 7 / 1 |

오른쪽은 50ms 늦은 프레임 대신 한 프레임 앞 프레임(66.7 - 50 = 16.7ms 앞)과 묶여 차이가 오히려 작습니다. 최대 84.6ms는 프레임이 빠진 자리에서 이전 프레임을 다시 쓴 경우입니다.

## 5. 시각 어긋남별 추적 지표

조건은 `scripts/eval_tracking.py --config configs/four_cam.yaml --tracker robust --fps 15 --frames 225 --seeds 0,1,2`이고, 어긋남은 좌우 카메라에만 넣었습니다(`--cam-skew-ms 0,0,S,S`, 허용 오차 25ms, hold). 정답은 기준(전방) 카메라 시각의 물체 위치입니다. 결과 JSON은 `out/measure/14_track_*.json`입니다.

| 어긋남 | ID 바뀜(보정 끔 / 켬) | 물체당 트랙 수(끔 / 켬) |
|---|---|---|
| 0ms | 26 / 26 | 1.667 / 1.667 |
| 20ms | 25 / 27 | 1.667 / 1.708 |
| 50ms | 20 / 20 | 1.5 / 1.5 |

| 어긋남 | 놓침 비율(끔 / 켬) | 한 물체 중복 표시(끔 / 켬) |
|---|---|---|
| 0ms | 0.0176 / 0.0176 | 67 / 67 |
| 20ms | 0.0188 / 0.0191 | 53 / 52 |
| 50ms | 0.0176 / 0.0182 | 47 / 59 |

묶은 뒤 남은 차이는 20ms 조건에서 20ms, 50ms 조건에서 16.7ms입니다. 15fps에서는 가장 가까운 프레임과 묶이므로 50ms 어긋남이 20ms보다 덜 어긋난 채로 들어갑니다. 예전 평가 방식(시간 맞춤 없음)의 같은 조건 ID 바뀜은 28회라 0ms 결과 26회와 비슷합니다. 세 어긋남 사이의 차이는 방향이 일정하지 않고, 같은 조건 안에서도 seed마다 ID 바뀜이 4~12회로 흔들려(보정 끔 기준) 조건 차이보다 큽니다. 합성 파일과 같은 조건(좌 20ms, 우 50ms, 우 5% 누락, 흔들림 1ms)은 ID 바뀜 15회, 물체당 트랙 1.417개였습니다.

마주 오는 차를 더한 조건(`--oncoming`, 왼쪽 차로 상대 25 m/s)은 다음과 같습니다.

| 어긋남 | ID 바뀜(보정 끔 / 켬) | 물체당 트랙 수(끔 / 켬) |
|---|---|---|
| 0ms | 79 / 79 | 2.615 / 2.615 |
| 20ms | 69 / 67 | 2.282 / 2.257 |
| 50ms | 87 / 83 | 2.539 / 2.462 |

어긋남이 없어도 ID 바뀜이 79회로 늘어납니다. 0ms 조건의 79회 중 37회가 마주 오는 차, 21회가 사람(상대 12 m/s), 18회가 옆 차로 차에서 나왔습니다(`--events`로 확인). 15fps에서 이 차는 한 프레임에 1.67m를 움직이고, robust 추적기가 이 속도를 따라가지 못하는 것으로 보이지만 원인 분석은 확인 필요입니다. 위치 보정은 2~4회 줄이는 정도입니다. 계획 4.4절의 "동기 오차가 33ms 넘게 벌어지면 타임스탬프 보정 추가"는 코드로 준비했지만, 효과 판정은 빠른 물체 추적을 고친 뒤 다시 해야 합니다.

## 6. 파이 실측: CSI 2대 + 가짜 측면 2대

설정은 `configs/four_cam_mixed.yaml`입니다. 전방(ov5647, 768x576)과 후방(Camera Module 3, 768x432)은 CSI 30fps이고, 좌우는 파이에서 만든 `out/sim4/cam2.mp4`, `cam3.mp4`를 30fps 속도로 읽는 가짜 USB 카메라입니다. 실행 조건은 Hailo 검출만(세그 없음, DX-M1 쓰지 않음), 탑뷰 화면, robust 추적기, 워밍업 30프레임, 20초(측정 구간 18.2초)입니다.

```bash
timeout -s INT -k 10 50 python scripts/run_demo.py --config configs/four_cam_mixed.yaml --backend hailo --headless \
    --duration 20 --warmup 30 --profile --profile-out out/measure/14_pi_four_cam_sync.json --sync \
    --sync-csv out/measure/14_pi_sync.csv --tracker robust --health-csv out/measure/14_pi_health_sync.csv \
    --health-interval 10 --hailo-stop-temp 95
```

| 구성 | FPS | 프레임 전체 평균 |
|---|---|---|
| 시간 맞춤 켬(`--sync`) | 15.84 | 62.8ms |
| 시간 맞춤 끔 | 16.16 | 61.6ms |

| 단계 | 켬 평균 | 끔 평균 |
|---|---|---|
| 카메라 획득 | 1.9ms | 1.7ms |
| 전처리 | 7.4ms | 7.6ms |
| Hailo 추론(4장 한 묶음) | 21.6ms | 21.6ms |
| BEV 합성 | 19.6ms | 20.0ms |
| 렌더링 | 10.8ms | 10.3ms |

두 구성 모두 4대 기준 8 FPS 목표를 넘었습니다. 시간 맞춤 자체의 비용은 FPS 차이 0.3 정도로, 두 실행 사이 장면 차이(켬 실행에서만 검출 269개)와 겹쳐 따로 가르지는 못했습니다. 가장 오래된 카메라의 센서 시각에서 화면 완성까지는 평균 107ms(켬)와 107.9ms(끔)였습니다. 카메라 4대에서는 Hailo 추론과 BEV 합성이 비슷한 크기의 큰 몫입니다.

파이에서 묶은 결과(기준 전방, 허용 오차 25ms, hold)는 다음과 같습니다.

| 카메라 | 차이 평균, 최대 | ok / hold / blank |
|---|---|---|
| 후방(CSI) | 2.4ms, 66.5ms | 303 / 15 / 0 |
| 왼쪽(가짜 USB) | 18.0ms, 48.1ms | 313 / 5 / 0 |
| 오른쪽(가짜 USB) | 18.0ms, 46.9ms | 315 / 3 / 0 |

CSI 두 대는 서로 따로 도는 30fps라 실행마다 위상이 달라집니다. 같은 날 첫 실행에서는 후방 차이 평균이 16.9ms였습니다. 가짜 USB 쪽은 부호를 살린 평균이 왼쪽 -5.1ms, 오른쪽 -7.2ms이고 범위는 약 -24ms에서 +48ms입니다. 가짜 카메라는 30fps로 아무 때나 도착하므로 가장 가까운 프레임과도 평균 18ms 정도 떨어집니다. 첫 실행 때는 hold가 "직전 묶음 프레임만 다시 쓰기"여서, 새 프레임이 허용 오차 밖 앞쪽에 계속 도착하는 동안 같은 옛 프레임이 최대 1168ms 묵었습니다(hold 198회. 이 실행의 파일은 다시 잰 결과로 덮여 화면 출력으로만 남아 있습니다). hold를 "가진 프레임 중 가장 가까운 것"으로 고친 뒤 최대 48ms로 줄었고, 위 표는 고친 뒤 값입니다.

온도는 Hailo-8이 실행 전 77.5~81.9도, 20초 실행 뒤 83.4~87.5도였고 SoC는 56~62도, throttled 0x0이었습니다. 95도 멈춤 조건에는 닿지 않았습니다. 온도 기록은 `out/measure/14_hailo_temp.log`, `14_pi_health_*.csv`입니다.

## 7. 이 측정이 빠뜨린 것

측면 카메라가 파일이라 USB 전송과 MJPEG 해제 비용, USB 대역폭 한계가 빠져 있습니다. 쿼드 키트는 4대를 켜면 카메라당 1152x648, 프레임레이트 절반이 되므로 실제 키트의 FPS와 칸별 지연, 칸 순서는 확인 필요입니다. 동기 오차는 파일 시각과 받은 시각으로만 쟀고, 계획 4.4절의 LED나 밀리초 타이머 촬영 실측은 아직입니다. 도로 세그(DX-M1)를 함께 돌린 4대 FPS도 재지 않았습니다(DX-M1 방열 전).

## 8. 시험

맥 `/usr/bin/python3 -m pytest -q`는 270개 통과, 4개 건너뜀입니다. 파이 `.venv`는 273개 통과, 1개 건너뜀입니다. 새 시험은 `tests/test_four_cam.py` 19개입니다. 기록은 `out/measure/14_pytest_mac.log`, `14_pytest_pi.log`입니다.
