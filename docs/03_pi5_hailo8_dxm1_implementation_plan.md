# 라즈베리파이 5 + Hailo-8 + DX-M1 구현 계획

이 문서는 라즈베리파이 5 한 대에 Hailo-8과 DEEPX DX-M1을 함께 붙여 테슬라 리얼리티 뷰와 비슷한 주변 시각화를 만드는 구현 계획입니다. 장비를 어떻게 연결하는지, 카메라를 몇 대 어디에 다는지, 어느 NPU에 어떤 모델을 맡기는지, 어떤 순서로 만들고 단계마다 무엇을 보고 끝났다고 판단하는지를 정리했습니다.

테슬라 쪽 구조와 수치는 [01. FSD v15 리얼리티 뷰 기술 조사](01_fsd_v15_reality_view_research.md), NPU 사양은 [02. 엣지 NPU 사양 비교](02_edge_npu_spec_comparison.md), 연산자 지원과 BEV 모델 비교는 [엣지 NPU 구성과 모델 선정](edge_npu_model_selection.md), 지금 있는 데모 코드는 [1단계 데모](phase1_demo.md)에 있습니다. 여기서는 그 내용을 다시 설명하지 않고 필요한 곳에서 연결만 합니다.

## 1. 한눈에 보는 결론

| 항목 | 계획 |
|---|---|

| 생성형 렌더러 | 테슬라 v15 방식(약 1B 생성 모델)은 이 세 장비로는 범위 밖으로 두고, 마지막에 가능성만 따로 시험합니다. 이유는 02 문서 3장에 있습니다. |

## 2. 하드웨어 구성

### 2.1 두 NPU를 한 대의 파이에 연결하는 방법

라즈베리파이 5는 외부로 나오는 PCIe가 x1 한 레인뿐이므로, PCIe 스위치가 들어간 듀얼 M.2 HAT로 이 레인을 두 NPU에 나눠 줍니다. 구성은 Seeed PCIe 3.0 to Dual M.2 HAT(103110065)의 두 슬롯에 Hailo-8 M.2 모듈과 DX-M1 4GB 모듈을 하나씩 꽂는 것입니다.

이 보드는 ASMedia ASM2806 PCIe 3.0 스위치를 쓰고, M-key 슬롯 2개가 각각 PCIe 3.0 x1로 연결되며 2230부터 2280까지 길이를 받습니다 [P1]. Seeed 위키에는 이 보드에서 Hailo-8을 돌린 결과(PCIe 3.0에서 187 FPS)가 실려 있습니다 [P2]. 다만 Hailo는 이런 서드파티 스위치 보드를 공식 검증하지 않으며, FPC 케이블만으로는 여러 장치에 전원이 부족할 수 있고 일부 스위치는 NVMe에 맞춰져 있어 인식 문제가 생길 수 있다고 안내합니다 [P3]. SSD와 Hailo를 같은 스위치에 물렸을 때 Hailo가 인식되지 않았다는 사례도 있습니다 [P4]. 그래서 M.2 슬롯 두 개는 모두 NPU에 쓰고, 저장장치는 SD 카드나 USB SSD로 둡니다.

대역폭은 문제가 되지 않을 것으로 봅니다. 두 NPU가 Gen3 x1(약 1GB/s)을 나눠 쓰더라도, 카메라 4대 입력을 10 FPS로 보내는 데 필요한 양은 약 21MB/s 수준입니다(모델 선정 문서 2.1절 계산). Hailo-8은 온보드 메모리가 없어 큰 모델을 돌리면 가중치를 계속 주고받는데, 이 계획에서는 Hailo-8에 작은 모델만 맡기므로 이 문제도 피합니다.

DX-M1은 4GB 메모리 모듈을 씁니다. 3장에서 세그멘테이션, 깊이 추정, FlashOcc 백본처럼 가중치가 큰 모델을 DX-M1에 맡기는 근거가 이 온보드 메모리입니다.

### 2.2 전원과 발열

파이5와 NPU HAT 하나만으로도 13~15W를 쓰므로 27W 공식 어댑터가 필요하다고 알려져 있습니다(모델 선정 문서 2.1절). 여기에 NPU가 하나 더 붙으므로, 전원은 27W 어댑터를 기본으로 하되 듀얼 HAT에 보조 전원 입력이 있으면 함께 연결합니다. 두 NPU를 동시에 오래 돌렸을 때의 실제 소비전력은 공개된 수치가 없어 확인 필요입니다. 쿨러는 파이 액티브 쿨러를 달고, 각 NPU 모듈에도 방열판을 붙입니다.

### 2.3 카메라 수와 배치

| 구성 | 카메라 | 연결 | 덮는 범위 | 쓰는 단계 |
|---|---|---|---|---|
| 2대 | Camera Module 3 Wide 2대 (수평 102도, 수직 67도, 1080p50) [P5] | CSI0 전방, CSI1 후방 | 앞뒤 약 102도씩, 좌우 측면은 사각지대 | 0~2단계 |
| 4대 | Arducam 12MP IMX708 쿼드 카메라 키트 (카메라당 수평 100도) [P6] | 4대를 2x2로 합친 한 프레임을 CSI 하나로 받음 | 100도 x 4 = 400도로 360도를 덮고 모서리에서 조금 겹침 | 3단계 이후 |

카메라 위치와 각도는 [configs/two_cam.yaml](../configs/two_cam.yaml)과 [configs/four_cam.yaml](../configs/four_cam.yaml)의 값을 출발점으로 씁니다. 차량 좌표는 X가 전방, Y가 좌측이고 원점은 뒷바퀴 축 중앙 바닥입니다. 4대 구성에서 전방은 1.3m 높이에서 12도, 후방은 1.1m 높이에서 15도, 좌우는 사이드미러 위치(1.05m)에서 30도 아래로 숙입니다. 좌우 카메라를 많이 숙이는 이유는 지면 투영 방식에서 차 바로 옆 바닥이 잘 보여야 거리 오차가 줄기 때문입니다. 테슬라는 카메라 7~8대를 쓰며(01 문서 6장), 이 계획의 4대는 그중 전방 와이드, 후방, 좌우 리피터 위치를 대신하는 최소 구성입니다.

쿼드 키트에는 주의할 점이 있습니다. 4대를 켜면 카메라당 해상도가 1152x648로 줄고 프레임레이트가 절반이 됩니다. 또 제품 페이지에 4대 전체가 하드웨어 동기화된다고 적혀 있으면서도, 0번과 1번, 2번과 3번이 각각 동기화되고 2번과 3번이 한 프레임 늦다는 설명이 함께 있습니다 [P6]. 파이5 지원 여부도 확인 필요입니다. 그래서 3단계에서 동기 오차를 직접 재는 것을 완료 조건에 넣었습니다. 카메라당 1152x648은 NPU 입력(640x640 이하)보다 크므로 해상도 자체는 충분합니다.

쿼드 키트가 파이5에서 동작하지 않으면 CSI 2대와 USB 카메라 2대를 섞는 구성으로 바꿉니다. 이 경우 USB 쪽은 하드웨어 동기화가 없으므로, 타임스탬프가 가장 가까운 프레임끼리 묶는 방식으로 처리합니다.

## 3. NPU별 모델 배치

### 3.1 나누는 원칙

두 NPU 모두 CNN은 잘 돌리지만 BEV 변환에 필요한 grid_sample, scatter 같은 연산은 사실상 지원하지 않습니다(모델 선정 문서 3장). 따라서 NPU에는 CNN만 올리고, 기하 변환은 CPU에서 합니다. 그 위에서 두 NPU의 성격에 맞춰 일을 나눕니다.

Hailo-8은 라즈베리파이용 모델 주와 데모 코드가 이미 맞춰져 있고 온보드 메모리가 없으므로, 매 프레임 돌아야 하는 작은 검출 모델을 맡깁니다. DX-M1은 4GB 온보드 메모리가 있어 가중치가 큰 모델이나 여러 모델을 함께 올리기에 유리하므로, 세그멘테이션과 깊이 추정처럼 무겁지만 몇 프레임에 한 번 돌려도 되는 모델을 맡깁니다. 이렇게 나누면 두 NPU가 같은 프레임을 동시에 처리하고, CPU는 두 결과를 합치기만 하면 됩니다.

### 3.2 단계별 배치표

| 단계 | Hailo-8 | DX-M1 | CPU |
|---|---|---|---|
| 1단계 | YOLOv8s 검출(Model Zoo HEF, NMS 내장), 도로 세그 HEF 선택 | 사용 안 함 | IPM 합성, 접지점 변환, 병합, 추적, 렌더링 |
| 2단계 | YOLOv8s 검출, 카메라 전체를 배치로 매 프레임 | 도로 세그(N프레임마다), 이후 단안 깊이로 거리 보정 | 위와 같음, 두 NPU 결과 시간 맞추기 |
| 3단계 | 위와 같음, 카메라 4대 | 위와 같음, 카메라 4대 | 쿼드 프레임 분할, 4대 IPM |
| 4단계 | FlashOcc 뒷부분(BEV 인코더와 occupancy 헤드) | FlashOcc 앞부분(이미지 백본과 깊이 헤드) | BEVPool, channel-to-height reshape, occupancy 렌더링 |

DX-M1용 모델은 Ultralytics에서 바로 만들 수 있습니다. `model.export(format="deepx")`로 .dxnn 파일이 나오고, 검출, 세그멘테이션, 시맨틱 세그멘테이션, 깊이 추정을 지원합니다. 시맨틱 세그멘테이션과 깊이는 YOLO26에서만 됩니다. 내보내기는 x86-64 리눅스에서만 되고 파이5에서는 실행만 합니다. INT8만 지원하며 보정 이미지는 실제 장착 카메라 영상과 비슷한 것을 넣어야 합니다 [P7]. 같은 문서에 파이5와 DX-M1에서 YOLO26n 검출 34.6ms, YOLO26n-seg 53.8ms(전후처리 제외)로 나와 있습니다 [P7].

4단계에서 앞부분을 DX-M1에 두는 이유는 카메라 수만큼 반복되는 이미지 백본이 가장 무겁고 가중치도 크기 때문입니다. 뒷부분은 BEV 격자 하나에 대한 2D conv라 가벼워서 Hailo-8에 둡니다. 이렇게 하면 프레임 t의 백본을 DX-M1이 처리하는 동안 프레임 t-1의 BEV 인코더를 Hailo-8이 처리하는 파이프라인이 됩니다. 다만 Hailo-8은 HEF 두 개(검출, BEV 인코더)를 번갈아 돌리면 컨텍스트 전환 비용이 생기므로, 4단계에서 뒷부분도 DX-M1에 두는 배치와 비교해 빠른 쪽을 고릅니다.

### 3.3 목표 처리 시간

화면 갱신 목표는 카메라 2대 기준 10 FPS, 즉 한 사이클 100ms입니다. 1단계 데모를 클라우드 x86 CPU에서 재 보니 2대 기준 BEV 합성 약 19ms, 렌더링 약 40ms였고 파이5에서는 몇 배 느릴 것으로 봅니다([1단계 데모](phase1_demo.md)). 따라서 병목은 NPU보다 CPU 쪽일 가능성이 크고, 1단계에서 가장 먼저 CPU 단계별 시간을 실측합니다. 느리면 BEV 해상도를 0.05m에서 0.1m로 키우거나, 바닥 영상 합성을 끄거나, 렌더링을 별도 스레드로 분리합니다.

## 4. 구현 단계와 완료 기준

순서는 아래와 같습니다. 연산자 확인(4.5)은 PC에서 컴파일러만으로 할 수 있으므로 0~3단계와 함께 진행해도 됩니다.

```
0단계 장비 확인 -> 1단계 Hailo 단독 실기 -> 2단계 DX-M1 추가 -> 3단계 카메라 4대 -> 4단계 FlashOcc 분할 실행 -> 5단계 자체 데이터
                    (PC에서 병행) 연산자 확인 (4단계 전까지)
```

### 4.1 0단계: 장비 연결과 개별 동작 확인 (약 1주)

듀얼 M.2 HAT에 두 NPU를 꽂고 PCIe Gen3를 켭니다(`dtparam=pciex1_gen=3`). Hailo는 `hailortcli fw-control identify`, DX-M1은 `dxcli -s`로 확인합니다 [P7]. DX-M1 런타임은 DX-RT 패키지(`dxrt-driver-dkms`, `libdxrt-bin`)를 설치하고 Python에서는 `dx_engine`의 `InferenceEngine`을 씁니다 [P7][P8]. DEEPX 설치 문서는 지원 OS로 Ubuntu와 Debian 12/13을 들고 Raspberry Pi OS를 따로 적지 않았으므로 [P8], 파이 OS에서 드라이버가 빌드되는지가 첫 관문입니다. 두 NPU에서 드론 검출 모델을 돌려 본 환경이 있으니 그 설치 상태를 그대로 출발점으로 씁니다.

완료 기준은 다음과 같습니다. 두 NPU가 한 부팅에서 함께 `lspci`에 보이고 각자 확인 명령에 응답합니다. 각 NPU에서 YOLOv8s를 단독으로 돌린 FPS를 기록합니다. 두 NPU를 동시에 30분 돌리는 동안 `vcgencmd get_throttled`가 0x0을 유지하고 PCIe 오류 로그(`dmesg`)가 없습니다.

### 4.2 1단계: Hailo-8 단독으로 기존 데모 실기 검증 (1~2주)

기존 데모의 `HailoBackend`와 `PiCameraSource`는 아직 실제 보드에서 돌려 보지 않았습니다([1단계 데모](phase1_demo.md)). 이 단계에서는 카메라 2대와 Hailo-8만으로 데모를 실제로 돌리고, HEF 출력 형식이 다르면 `parse_hailo_nms`를 맞춥니다. 이어서 내부 파라미터와 외부 파라미터를 보정하고, 바닥에 줄자로 잰 위치에 차량이나 사람을 세워 거리 오차를 잽니다.

완료 기준은 기존 문서에서 정한 값을 그대로 씁니다. 내부 보정 RMS 1px 이하, 외부 보정 지면 역투영 오차 10cm 이내([1단계 데모](phase1_demo.md)), 카메라 2대 10 FPS 이상, 5m 이내 차량 위치 오차 0.5m 이하([모델 선정](edge_npu_model_selection.md) 5장)입니다. 여기에 CPU 단계별 처리 시간(투영, 병합, 추적, 렌더링)을 표로 남기는 것을 더합니다.

### 4.3 2단계: DX-M1 추가와 두 NPU 동시 실행 (1~2주)

`realityview/detectors.py`에 DX-M1용 백엔드를 추가합니다. 처음에는 같은 YOLOv8s를 두 NPU에 각각 올려 같은 녹화 영상으로 FPS와 검출 결과 차이를 비교합니다. 이 비교로 두 NPU의 실제 처리 능력을 한 번 맞춰 본 뒤, 검출은 Hailo-8, 도로 세그는 DX-M1으로 나눕니다. 두 NPU는 스레드를 나눠 동시에 돌리고, 세그는 기존 설정처럼 3프레임마다 실행합니다. 세그 결과가 늦게 도착하면 가장 최근 마스크를 그대로 씁니다.

완료 기준은 다음과 같습니다. 두 NPU를 함께 쓸 때의 FPS가 1단계보다 낮아지지 않습니다. 같은 녹화 영상 100프레임에서 두 NPU의 검출 결과를 비교한 표(FPS, 검출 수, 위치 차이)가 있습니다. 직접 도로를 칠한 20프레임에서 도로 마스크 IoU를 재고 기록합니다. IoU 목표치는 처음 측정값을 보고 정하며, 지금은 정하지 않습니다.

이 단계 끝에 YOLO26 깊이 모델을 DX-M1에 올려, 지면 평면 가정으로 계산한 거리와 비교해 봅니다. 경사로처럼 평지 가정이 틀어지는 곳에서 오차가 줄어드는지가 확인할 점입니다.

### 4.4 3단계: 카메라 4대로 확장 (1~2주)

쿼드 키트를 연결하고, 2x2로 합쳐진 프레임을 카메라 4개로 잘라 기존 파이프라인에 넣는 소스를 추가합니다. `configs/four_cam.yaml`을 실제 보정값으로 교체합니다. 동기 오차는 4대 모두가 볼 수 있는 곳에 깜박이는 LED나 밀리초 타이머 화면을 두고 찍어서 잽니다.

완료 기준은 다음과 같습니다. 카메라 4대 기준 8 FPS 이상(쿼드 키트가 프레임레이트를 절반으로 줄이는 점을 감안한 목표), 카메라 간 동기 오차 실측값 기록, 차를 한 바퀴 도는 사람이 BEV에서 끊기거나 둘로 보이지 않고 같은 ID로 추적됩니다. 테슬라 대시캠에서 잰 카메라 간 시차가 최대 8.7ms였다는 보고가 있어(01 문서 7장), 동기 오차가 한 프레임(약 33ms 이상) 넘게 벌어지면 타임스탬프 보정을 추가합니다.

### 4.5 연산자 확인 (PC에서 0~3단계와 병행)

모델 선정 문서 3장에 적은 시험을 그대로 합니다. ResNet18+FPN 백본, FlashOcc의 BEV 인코더와 occupancy 헤드만 잘라낸 ONNX, grid_sample과 ScatterND만 있는 최소 모델, 이렇게 세 개를 Hailo DFC와 DX-COM에 넣어 컴파일 결과를 기록합니다.

완료 기준은 모델 선정 문서 3장 표의 "확인 필요" 칸이 모두 실측 결과로 바뀌는 것입니다.

### 4.6 4단계: FlashOcc 분할 실행 (4~8주)

모델 선정 문서 5장의 2단계 계획을 따릅니다. 백본을 ResNet18로 줄이고 입력 256x704, BEV 100x100으로 재학습하며, nuScenes 6대 중 4대만 쓰도록 데이터 로더를 바꿉니다. ONNX를 앞부분, 뒷부분 두 개로 나누고 BEVPool은 CPU에서 NumPy나 C로 구현합니다. 3.2절대로 앞부분은 DX-M1, 뒷부분은 Hailo-8에 올리고, 둘 다 DX-M1에 올린 경우와 비교합니다. INT8 보정 데이터는 3단계에서 실제 카메라로 찍은 영상을 씁니다.

완료 기준은 다음과 같습니다. PC의 FP32 모델과 NPU의 INT8 모델을 같은 검증 데이터에서 비교한 mIoU 차이를 기록합니다. 카메라 4대 기준 5 FPS 이상입니다(모델 선정 문서 비교표의 추정 3~8 FPS 가운데 값). BEVPool CPU 시간을 실측해 기록합니다. 실제 장착 카메라 영상에서 occupancy 결과가 1단계 방식(지면 투영) 결과와 크게 어긋나지 않는지 같은 장면을 나란히 놓고 확인합니다. mIoU 허용 하락폭은 FP32 결과를 본 뒤 정합니다.

### 4.7 5단계: 자체 데이터 수집과 미세조정 (선택)

nuScenes와 카메라 높이, 화각이 다르면 성능이 크게 떨어지므로, 실제 장착 카메라로 영상을 모아 1~3단계 결과를 의사 라벨로 써서 미세조정합니다(모델 선정 문서 5장 3단계). 완료 기준은 같은 장면에서 미세조정 전후 occupancy 결과를 비교한 기록입니다.

### 4.8 생성형 렌더러 가능성 시험 (범위 밖, 선택)

테슬라 v15의 렌더러는 약 1B 크기의 생성 모델이 영상을 직접 만드는 방식이고(01 문서 1장), Hailo-8과 DX-M1은 확산 모델 지원이 공개 자료로 확인되지 않았습니다(02 문서 2장). 그래서 이 계획의 결과물은 4단계까지의 "인식 결과를 3D로 그리는" 방식입니다. 그래도 시도해 보려면 4단계의 BEV 특징을 조건으로 받는 소형 CNN 생성기(경량 U-Net, 1~few step)를 DX-M1에 올려 저해상도 가상 시점 영상을 만드는 실험부터 할 수 있습니다. 이 방향을 본격적으로 하려면 8GB 메모리가 있는 Hailo-10H가 더 맞습니다(02 문서 4장).

## 5. 위험 요소와 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 듀얼 M.2 HAT에서 한 NPU가 인식되지 않음 | 두 NPU 동시 사용 불가 | 보조 전원 연결, PCIe Gen2로 낮춰 시험, 안 되면 파이 두 대에 NPU를 하나씩 달고 결과만 이더넷으로 주고받기 |
| DX-RT 드라이버가 Raspberry Pi OS에서 빌드되지 않음 | DX-M1 사용 불가 | Ubuntu for Raspberry Pi 설치, Radxa 문서 절차 따르기 |
| 쿼드 키트가 파이5에서 동작하지 않음 | 4대 구성 지연 | CSI 2대 + USB 2대, 타임스탬프 기반 묶음 |
| 파이5 CPU가 BEV 합성과 렌더링을 못 따라감 | FPS 목표 미달 | BEV 해상도 낮추기, 렌더링 스레드 분리, 핵심 루프 C 확장 |
| 지면 평면 가정 오차 | 원거리, 경사로 거리 오차 | 2단계 깊이 보정, 4단계 occupancy |
| FlashOcc INT8 정확도 하락 | 4단계 결과 품질 저하 | 혼합 정밀도 가능 레이어 확인, 보정 데이터 늘리기 |

## 6. 시작 전에 정해야 할 것

카메라를 실제 차량에 달지, 아니면 소형 이동체나 책상 위 모형으로 먼저 시험할지 정해야 합니다. 모형으로 시험할 경우 설정 파일의 카메라 높이와 BEV 범위를 줄이면 됩니다.
